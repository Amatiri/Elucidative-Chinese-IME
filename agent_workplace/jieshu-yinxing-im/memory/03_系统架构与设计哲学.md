## 三、系统架构与设计哲学

### 7800+字码表的覆盖率与适用场景

**码表目前收录约 7900 个汉字（及1600+词语），零重码体系完整。对于诗词等很少依赖词语库的文本，纯单字编码已能覆盖绝大部分需求。**

**码表对诗词文本的高适配性**：

- 诗词用字量远小于现代散文——字字独立，不依赖词语库——零重码纯粹度更高
- 同部首字编码一致性直观可见（山/水部集合落 u 列等）
- 多音字自动并列，天然形成对比学习材料
- 未录字直接点名，码表边界一览无余

**此覆盖率对教学的支撑**：每首诗都是现成的编码练习材料——打散全诗编码当教学案例，学生看到的是「每个字都在码表里、都可以查证」的全景，而非「只学了几个示范字」。

### 解书音形的定位与哲学

> 来源:开发者核心阐述

**定位**:为深度汉字爱好者打造的、以**认知效率**为核心的汉字认知模型,而非服务大众的普适输入工具。

**高门槛的本质**:

- 陡峭学习曲线 = 非优化不足的败笔,而是主动付出的「理解税」
- 目的:维护汉字理据性尊重 + 编码体系逻辑自洽
- 内置的容错性与辅助机制,允许学习者分期缴纳此税,以错误路径或粗糙认知也能打出字,保护学习信心,但这并不降低门槛本身,而是让门槛变得**可跨越**

**渐进性**:在单一精密系统内垂直深化

### 仓库内容原则

**仓库 `D:\USB\Py\输入法\`(码表 + 前端 + 规则的载体)的内容有且只有以下三类**:

1. **码表本身**: `dictionary.txt` / `dictionary_no_number.txt` / `ciyu.txt`
2. **前端与规则**: `ime.py` / `main.py` / `config.py` / `manager/` / `help/`/`README.md`

**禁止向仓库根目录添加**:

- 临时性工作产物(如 `ciyu_review.txt` 待审清单)
- 与码表/前端/规则无直接关联的工具脚本
- 调试输出、日志、缓存、缓存文件
- 个人笔记、参考材料、二次实验代码

**仓库是给普通用户看的透明化展示**,不是可以随便增删的混乱区。新增/修改/删除任何文件都要问"这能否直接服务于码表、前端或规则之一?"——答否则不增。

**附带原则**:

- 工程产物(临时清单、工具脚本输出)应放 `scripts/` 或工作目录,**不放**仓库根目录

- `other/` 已经是"历史实验代码"收容所,新增实验性内容可走 `other/` 而非仓库根目录

- `.gitignore` 列出所有不应被版本控制的产物

- 学习者分阶段掌握音、形规则,知识层层叠加

- 进阶是对已有认知的**补充**而非推翻,最终形成完整的分析思维

- 辅助机制(剩余编码提示、部首表显示等)是攀登途中的路标与踏板,而非直达电梯--它们服务于学习深度,而非输入速度

### 码表为中心的核心架构

**核心观点**:码表是一性的(第一性),规则是事后对既有编码的解释性归纳(第二性)。与传统"先有规则再生成编码"的方案相反。

**三层辐射结构**:

- **地基层**:`dictionary.txt`——编码的物理载体,一切的真实源头
- **规则层**:`rules.md` / 键位图 / PPT——对码表的解释与教学
- **使用层**:`main.py` / `ime.py`——基于码表的查询与输入

**"挂表运行"的含义**:码表就是 API。拿走所有代码,码表依然完整可读——每个字的编码、读音、排序都在里面。

**四大连锁后果**:

1. 零依赖启动:只需码表即可开始编码推导
2. 规则不崩溃:规则改错了不影响码表,码表仍是唯一真相
3. 离线即完整:不依赖网络、数据库、云端计算
4. 人的判断是终极裁决者:规则 vs 码表冲突 → 以人的确认为准(而非程序自动裁决)

### 去重的本质与异体字补码的一对多模式

**去重的本质是映射的一一性**,粒度分层:

- **单字三步去重**:同一读音下,A/B/C/D/E 五码组合唯一
- **词语一步去重**:同一读音下直接去重,根源是词语数据的语义已被人的判断先行消解(不会同时录入两个同音同码词语)

**异体字补码揭示的深刻模式**:同一汉字在同一个音区有多个合法编码路径时:

- **路径不同(源字不同)** → 共存,如繁体补码保留独立行
- **路径相同(源字相同)** → 去重

这与多音字的处理逻辑共享同一个**一对多宽容模式**:只要入口不同,就保留;入口相同则只需其一。

**词语压缩与异体字补码的不同策略**:

- 词语的一对多:精度差异 → 合并为一行用空格分隔
- 异体字的一对多:质差(不同源字入口)→ 保留多行共存

**架构的成长模式**:两次修改(词语压缩、异体字补码)都在现有管道中插入新判断逻辑,管道本身骨架不动——管道稳定但每个阶段的判断规则可以独立进化,是非刻意设计但结果极好的自然涌现架构。

### 解书音形设计哲学(认知翻译视角)

**解书音形不是教用户认字**,而是把用户已有的汉字认知翻译成编码。用户越懂汉字本身,编码越自然。

**记忆文档的定位**:记忆文档(memory.md)是弥补 AI 缺失视觉和语感的显式规则,是人类直觉的翻译版。人类用户不需要它——人类通过观察字形结构和查阅字典就能直接获取信息,不需要规则推导。解书拆分是视觉结构的编码转写,不是需要额外学习的规则体系。

**学习者的核心途径**:建立在已有汉字功底上——听、说、读、写、查的能力直接决定编码准确度。

### 编码体系设计哲学(程序角色与零重码)

**程序角色是中性执行器**:只保证零重码,不提供编码建议。编码质量完全由规则文档、开发者审核、用户反馈维护。

**用户自定义空间分三层**:

1. **规则内调整**:在规则框架内选择部首、副码路径
2. **完全绕过规则**:直接指定编码,程序不做规则校验
3. **空码区自由分配**:未被占用的编码空间可由用户自行分配

**零重码是唯一不妥协的硬约束**:支撑前缀匹配、自动拆分、全码精确命中等全部体验。

**规则文档不是程序的辅助补丁**,而是系统真正的核心,程序是其外壳。解书音形是将编码体系从程序逻辑中剥离成纯数据的设计。

**人工编码的认知复利**:强制每次录入都把规则体系从头到尾推一遍——每录入一字是学习而非负担。`batch_entry` 批量录入的设计意图不是降低效率,而是创造推导条件——提供同音区参照、冲突即时裁决,让程序消除杂务但人的判断不能跳过。

### 形码的动态段与静态段

解书音形形码分两段设计:

- **动态段**(决定取哪个部件):承载所有认知复杂度——部首选择(优化分配)、余字拆分(一般余集合选取)、余部首传递。这是人需要动脑的部分。
- **静态段**(查表得到编码):纯机械映射——部首表查码、表外部首处理。这是查表即可完成的部分。

**两段解耦的意义**:

- 规则变更(动态段)不影响部首表(静态段)
- 部首表扩充(静态段)不需要修改规则(动态段)
- 各段独立进化,互不锁死

### 编码中字母重复不构成退化

**核心纠正**:主副码同字母、初副码同字母,甚至初主副三码同字母,都不构成编码退化。字母相同不等于信息为零。

**根本原因**:编码的每一位来自不同的推演路径--初码来自双拼声母,主码来自部首码或独体构形,副码来自余部/余音分析。同一字母在不同位置指涉完全不同的部件或来源,这是巧合,不是冗余。

**实例**:

- 伧 ch1rr:主码 r = 亻,副码 r = 仓的部首 人。两码说两件事,看到 rr 反而提示「左人右亦涉人」→ 伧
- 汕 uj1uu:初码 u = sh声母,主码 u = 氵,副码 u = 山的余音。三码同字母,三码三来源

**真正的退化**:发生在结构逻辑断裂--该取数字主码的独体字取了字母主码(如把 mu46 编成 mu4m),编码的结构承诺(数字=独体/字母=合体)错了,用户会被误导去寻找合体字部件。

**教训**:判断退化看的是「编码是否正确描述了字形结构」,不是「字母有没有重复」。字母重复往往是递归或巧合,本身携带信息--它提示了整字部首和余集合之间的某种相似性。

###### 合体字表矩阵

合体字表矩阵的维度含义:

- **列(D 码)**:对应部首,每个部首一列
- **行(E 码)**:对应副码类型(空副码/余音/余部)
- **格子**:对应编码三位交汇(音码+主码+副码),每格一个字或空

矩阵整体展示了在同一读音下,解书编码如何通过部首(列)和副码(行)的双重分流实现零重码--同一读音下的所有合体字被分布到不同的行列交汇点上,天然无碰撞。 

### 副码率指标

**空副码的三重设计价值**:

1. **按需分配**:主码扛九成区分责任,副码只在碰撞时激活
2. **缩短思考链**:大多数常用字无需推导副码,降低认知负担
3. **留出编码空间**:空出的副码位置为未来扩展(如补码、词语编码)留余地

**副码率作为音区健康度指标**:

- **冲突密集度**:该音区内需要副码来区分的字比例
- **学习成本衡量**:副码率高的音区需要更多推导步骤
- **饱和度预警**:理论上限为 26/27≈96.3%,达到 100% 不可能(违反"常用字空副码"原则)

### 自研前端的工程逻辑与字符集扩展

**字符集扩展**:解书音形使用数字和点作为合法编码字符,共 39 个字符(比主流输入法多 13 个)。数字承载声调和独体构形,点作为繁异体补码前缀。这是实现零重码的物理前提。

**自研前端的两个原因**:

1. **字符集不匹配**:数字在 Rime 体系里与候选选择键冲突
2. **特有优化机制被 Rime 架构锁死**:前缀匹配剩余编码、自动上字、副码 a 占空、结构锚点自动拆分、多字预览等 8 个核心机制中 5 个不能实现、3 个大改

**前端本质**:简单挂表运行——零重码使系统不需概率模型、N-gram、云联想、动态调频,只需要 `startswith` 线性扫描。

**候选列表角色**:候选列表是过渡界面而非最终界面——熟练用户靠剩余编码提示补全全码,不看候选行。

**跨平台缺失的根因**:各系统键盘输入架构不同(Windows TSF、macOS InputMethodKit、Linux IBus/Fcitx)。优先 Windows 是自主性最高 + 用户基数最大的工程决策。

**自动拆分条件 3 的语义**:连续两个数字→第二个后切,这是独体字的调码+主码封口(如 `yi41`),而非两个字的调码。条件 2 和条件 3 正交——条件 2 往前 2 位切,条件 3 在第二位数字后切,方向不同、互不排斥,`elif` 只是同轮互斥,`while` 保证先后各自生效。

### 解书音形的双重性：输入工具与汉字分析材料

解书音形具有双重面孔:

**面向操作的输入法面**:

- 前缀匹配、多字拆分、自动上字
- 追求操作流畅度
- 目标是"不用背,打就完事了"

**面向理解的汉字分析材料面**:

- 编码理据、余部传递、音似判定
- 追求汉字结构认知深度
- 编码过程本身就是对汉字结构的分析

**双重性是设计目的本身而非副产品**:同一套符号提供分层信息密度——对初学者是输入工具,对进阶者是汉字分析框架。两个面不是先后关系,而是始终并存,用户根据需要自行切换关注点。

### 词语编码策略:与小鹤音形的对比

**相同点**:二字词、四字词及长词的编码结果与小鹤音形一致。共享相同底层假设--初码(声母)是词语编码的最小编码单元,韵母用于拆解同声母歧义。

**分歧点(三字词)**:

- 小鹤:声+声+声韵(四码)
- 解书:声韵+声韵+声(五码)
- 根源:小鹤有四码定长约束,解书没有

### 五层同心圆

| 层级      | 核心表述                 | 一句话解释                |
| ------- | -------------------- | -------------------- |
| **目标层** | 知音辨形，高效输入            | 先靠音切入，再用形区分，目标是效率    |
| **权衡层** | 规范/直觉/效率平衡；常用优先、零重码  | 三方博弈，无绝对优先；高频短码，编码唯一 |
| **学习层** | 先用再学、实战为主；把已有认知翻译成编码 | 不要先背规则，先打起来；懂汉字就能懂编码 |
| **架构层** | 码表为中心；规则是解释性归纳       | 码表是唯一真相，规则只是对它的说明    |
| **系统层** | 程序是中性执行器；零重码是唯一硬约束   | 程序只保证不重码，质量由规则和人工维护  |

### 关键张力

- **认知效率 vs 理解税**：要获得「懂汉字就会打」的能力，必须前期付出理解规则的代价
- **码表第一性 vs 规则第二性**：先有编码，再用规则解释它——规则改错了不影响码表
- **动态段 vs 静态段**：部首选取/余字拆分（人动脑）与查表得码（机械映射）解耦

### 双重身份

解书音形同时是：

- **输入工具**：前缀匹配、自动上字，目标是「不用背，打就完事了」
- **汉字分析材料**：编码过程本身就是对汉字结构的分析

> **本质**：为深度汉字爱好者打造的、以认知效率为核心的汉字认知模型——用户越懂汉字，编码越自然。
