## 一、立词必要性判断(基于 word_filter.py)

### 现象:ignore 词表的真实过滤逻辑

`scripts/word_filter.py` 在筛选候选词进入 `ciyu_review.txt` 时,会跳过 `ciyu_review.ignore.txt` 中已列出的词。这份 ignore 表并非随机维护--背后有一套基于**输入流顺势性**的判断逻辑。

### 核心原则:顺势输入 > 立词收益

**用户在打一个词语时的真实操作流**:

1. 输入首字编码 → 候选出现 →是想要的字
2. 继续往后打下一字编码 → 字从同一段流的末尾追加
3. 用户**不会回头**到流的中间或开头去"等一个词条命中"

**关键观察**:

- 当首字已经能用两码(或更短)唯一确定时,立一个"词语编码 = 首字前两码 + 可能后续"几乎毫无意义。
- 用户实际体感:直接顺势接打第二字;而立词几乎不节省思考量,又占据码表空间,效率差。

### 判断流程(默认路径)

```
判断一个候选词是否值得立词:
  1 首字是否 2 码(或更短)即可唯一命中?
     ├─ 是 → 默认跳过,不立词
     │       (顺势接打第二字,立词不省码、反而碍事)
     └─ 否 → 进入 2
  2 立词后码长是否明显短于逐字?
     ├─ 是 → 立词
     └─ 否 → 跳过
```

### 顺势原则的双字版本:probe_word 双侧前缀覆盖

`word_filter.py` 中的 `probe_word(word)` 函数把顺势原则**形式化**为可执行脚本(仅适用于 2 字词,三字及以上人工判断):

- 不只判首字--而是**首字与末字分别检查**:各自取 `dictionary.txt` 中所有编码,逐个取前 2 码,调用 `query_by_prefix(prefix)`,看首选是否就是该字
- 两边都能被前缀覆盖 → 视为顺势可达 → 不立词
- 任意一边不能被前缀覆盖 → 进待审清单

```python
# word_filter.py 核心逻辑(节选)
def probe_word(word, dictionary_path, query_by_prefix_fn):
    c1, c2 = word[0], word[1]
    codes1 = load_char_codes(c1, dictionary_path)
    codes2 = load_char_codes(c2, dictionary_path)

    def char_coverable(char, codes):
        for code in codes:
            if len(code) < 2:
                continue
            prefix = code[:2]
            try:
                candidates = query_by_prefix_fn(prefix)
            except Exception:
                continue
            if _first_char_of(candidates) == char:
                return True
        return False

    return char_coverable(c1, codes1) and char_coverable(c2, codes2)
```

调用关系:`main()` 里 `probe_target = filtered[:args.probe_limit]` 限定了 probe 范围(默认 5000),保留目的是**避免长时间扫描**。`--no-probe` 开关可关闭,退回纯机械过滤。

**为什么 n=2 才用 probe**:三字及以上词的顺势判断未算法化、靠人工。原因有二:

- 三字及以上词在词库中占比远小于二字词
- 三字词的编码规则与二字词不严格同构(不与 `probe_word` 的"对末字 2 码覆盖"对齐)

这意味着,对二字词优先信赖 `probe_word` 的输出,对三字、四字词退回人工目测。

### 默认路径下"被忽略"的典型词

实证:用 `generate_jd_codes.find_shortest_code` 跑当前 ignore 词表,可观察到**首字简打 ≤ 2 码**的词占比约 70%+,示例:

| 词   | 首字  | 首字简打 | 首字全码 | 词简打    | 词全码       |
| --- | --- | ---- | ---- | ------ | --------- |
| 一种  | 一   | yi   | yi12 | yivs3h | yi12 vs3h |
| 资源  | 资   | zi   | zi1b | ziyr2u | zi1b yr2u |
| 生产  | 生   | ug   | ug11 | ugij3  | ug11 ij37 |
| 工业  | 工   | gs   | gs15 | gsye4  | gs15 ye45 |
| 农业  | 农   | ns   | ns24 | nsye4  | ns24 ye45 |
| 专业  | 专   | vr   | vr17 | vrye4  | vr17 ye45 |
| 之后  | 之   | vi   | vi12 | vihb4k | vi12 hb4k |
| 说道  | 说   | uo   | uo1y | uodk4z | uo1y dk4z |
| 民族  | 民   | mn   | mn24 | mnzu2f | mn24 zu2f |

> 这些词**首字两码就能拿到**--顺势打 `yi`+`vs3h`、`zi`+`yr2u` 已是最自然的输入。立一个 `yivs3h` 词条反而破坏操作流。

### 例外条件:极常用词可突破顺势原则

即使首字两码可得,**极少数极常用词仍会立词**。典型例子:

- **一样** `yiyh`:首字 `yi` 同样两码可得,但"一样"词频极高,立词后可显著降低总击键数、提升实际输入流畅度。

判断这种例外需要人工:**不能用纯规则覆盖,靠实际使用频率决定**。一旦决定立词,需同步从 ignore 表移除。

### 与其他维度的关系

顺势原则是主导,但**还有四条并行补则**也参与立词决策,互相独立,各自管一个维度:

| 维度        | 是否决定立词         | 说明                      |
| --------- | -------------- | ----------------------- |
| 首字简打长度    | **是(主导)**      | ≤2 码默认不立(probe 已形式化为双侧) |
| 词条语义(虚/实) | 否              | "资源"是实词也照样不录            |
| 词频        | 是(阈值突破)        | 极高词频可立词突破顺势原则           |
| 字数        | 否(二字词交给 probe) | 2 字、3 字、4 字词判断机制不同      |
| 字面可拆性     | 是(语义档分档)       | 见下方原则 4                 |

### 四条并行补则

#### 原则 1:避免连续词语"叠加冗余"

**不另立已能由原子词拼接的连续词语。**

原因:已有"打两个原子词 + 边界声明"近似实现,另加会使码表过度膨胀。

| 例子                   | 立词方案           | 词语组合方案                  | 对比        |
| -------------------- | -------------- | ----------------------- | --------- |
| 不立「发展经济」(已有「经济」「发展」) | `favjj;j`(7 键) | `favj`(空格)+`j;ji` = 9 键 | 已能近似,无需再加 |

**判定形式**:候选词 = 词库中已有词的字符拼接,且长度 ≈ 已有词语组合结果  → 倾向不立。

#### 原则 2:编码空间饱和 → 近音词不立

**词语编码空间有限,对发音相近的二字词,立词码长已逼近单字组合时节省量为零,不建议录入。**

`ciyu.txt` 词语编码规则大致按"首字 AB + 末字 AB + 末字其余编码"组合,二字词编码常在 4-5位左右。同时码表零重码约束意味着,**近音词占用同一编码空间**(如 `zuvi`、`djzi` 系列已被高词频占满)。

| 近音词情形 | 立词码长  | 逐字码长        | 节省          | 结论         |
| ----- | ----- | ----------- | ----------- | ---------- |
| 高频    | 4 位   | 4 + 4 = 8 位 | 4+          | 立词收益很大     |
| 中频    | 5 位   | 8位+         | 3+          | 立词仍有收益     |
| 低频    | 6 位++ | 8位+         | 1+且需要额外移动光标 | 立词无意义,建议不立 |

**判定形式**:候选词末字完整编码与词典中已有近音词末字编码重合 → 编码空间已被占满;同时该词立词码长 ≈ 逐字组合码长 → 不立。

**注意**:这条对二字词极敏感,对三字、四字词影响小(三字、四字词立词空间更宽松)。

#### 原则 3:字面可拆性的语义档分档(启发性概念,不形式化)

**字面可拆性并非"是否可拆"二值,而是按"语义组合紧密度"分两档。**

| 档位                       | 字面表现           | 例子(举例,非列举)           | 立词倾向              |
| ------------------------ | -------------- | -------------------- | ----------------- |
| **紧密组合**(组合产生新概念)        | 拆开后字义叠加 ≠ 整体语义 | 文化、经济、系统、说明、美丽       | 立(即使可拆仍需立)        |
| **松散并列**(两字语义修饰/并列,无新概念) | 拆开后字义叠加 ≈ 整体语义 | 各国、各省、各市、每个、英国、美国、法国 | 不立(顺势打即可,立词无压缩价值) |

**为什么这条与顺势原则不同维度**:顺势原则关注"打字的击键数",原则 4 关注"语义压缩空间"。一个松散组合词即便总码长较短、立词码长稍短,仍然因为字面就是两字并立不立词--**立词后的语义压缩价值低**。

**形式化保留态度**:这条分档是启发性概念不形式化,**不接入 `probe_word`,不接入 ignore 文件自动生成**。理由:

- 中文词语本身边界模糊,没有可靠的结构化判别依据
- 宁可保留人工判断的灵活度,也不要刚性规则制造假阳/假阴
- 实操中:用户问"该不该立 X 词"时,由回答者(人类或 AI)按这两档直觉区分

#### 与原则 1 的对比

原则 1(不叠连续词语)和原则 3(字面松紧分档)都会导致"不立词",但作用维度不同:

- 原则 1 是**机制层面**--已存在的原子词 + 它们的拼接 = 字符组合层重叠
- 原则 3 是**语义层面**--字面组合的紧密度 = 概念层压缩价值

同一条词语可能两层都不满足,但判别路径独立:原则 1 直接看字符,原则 3 需要理解语义。原则 3 不形式化就是为了避免把字符重叠机制和语义紧密度混进同一套规则里。

#### 补充：原则 4:高频首选字组合占位 → 避让

**候选词的最常用码若恰好等于某个高频首选字组合的逐字拼接码,不占用该码位,改用更长编码或不立词。**

高频首选字组合的拼接码天然很短(各字本身码短),占用代价极高:用户意图输入该字组合时会被 `query_phrase` 整段抢断(冲突机制见 04 文档 2(4))。低频组合(如 千眠、书茹发)则无此顾虑,由用户侧分隔避让即可。

| 词语  | 最常用码   | 处理                 |
| --- | ------ | ------------------ |
| 之一  | `viyi` | 高频组合(之+一),不立词,顺势输入 |
| 质疑  | `viyi` | 避让,改 `viyi2`       |
| 执意  | `viyi` | 避让,改 `viyi4`       |

**判定形式**:候选词最常用码 = 两个首选字的拼接码,且该字组合高频 → 避让(改长码或不立)。是否"高频"需人工裁量,与极常用词例外同理。**本条优先级高于立词收益判断**:即使词频达到"极常用例外立词"档,最简码撞上高频首选字组合时也只能降级用长码。

### 给 AI 的实操建议

收到用户问"为什么 X 词没在词库里"或"X 词要不要立词"时:

1. **先查 `find_shortest_code` 看首字简打长度**;二字词可优先信赖 `probe_word` 输出。
2. 如果首字 ≤ 2 码可得 → 默认答"顺势接打即可,立词意义不大"。
3. 如果用户指出"但这个词极常用" → 同意立词,并提示同时清理 ignore 表。
4. **避免给连续词语添立条目**(原则 1);如果候选是已有原子词的拼接 → 回答"顺势打两个原子词更合适"。
5. **检查编码空间**(原则 2:如果候选末字在码表已有多个近音词占据编码空间,且立词码长 ≈ 逐字组合 → 答"近音拥挤,建议不立或换词组"。
6. **语义档分档**(原则 3):对字面可拆词按"松散/紧密"分档判断--但**不要为分档硬找理由**:松散的直说不立,紧密的如可顺势也不立(顺势原则优先)。**这条仅作为势均力敌时的辅助参照,不作为独立否决依据**。
7. **查首选字避让**(原则 4):如果候选词最简码恰为高频首选字组合的拼接码(如 `viyi` 之于 之+一) → 答"避让该码位,改长码或不立"。

## 二、理据添加方法(基于 dictionary-data.js)

理据存储在 `help/webpage/dictionary-data.js` 的 `rationale` 对象中。以下是判定与撰写约定--具体脚本调用与文件路径参见 [references/tools.md](../references/tools.md)。

### 一句话原则

> **理据 = 字形看不出来的信息 + 码表上看不出来的信息。**

理据是查询入口,不是教学教案。只需回答两个问题:**主码部首是啥?副码字母指哪个部件?** 推导过程、规则术语、输入层影响均不属于理据字段。

### 三类冗余信息(不可写入理据)

| 冗余类型          | 示例(错)                   | 问题                     |
| ------------- | ----------------------- | ---------------------- |
| **字形已告诉你的事**  | `斛=角+斗`                 | 拆分部首肉眼可见,只需写非直觉那位(`斗`) |
| **编码已告诉你的事**  | `口(k)`、`金(j)`           | 编码第四位就是部首码,无需在理据里重复标字母 |
| **理解层/教学层的事** | `余部首传递`、`声旁演变`、`输入层需空格` | 属于编码文档和教学素材,不应塞进理据字段   |

### 必须保留的信息

| 信息类型       | 示例                  | 说明                      |
| ---------- | ------------------- | ----------------------- |
| **非直觉部首**  | 斛→`斗`(非角)、倝→`十`(非人) | 纠正直觉判断,字形上不容易猜到的部首选择    |
| **空副码字**   | `(四码→吃)`、`(四码→糊)`   | 不看码表不可能凭空知道,字形上看不出来     |
| **副码部件指向** | 槲→`角,副码d→核`、擀→`十`   | 副码字母对应的具体部件,字形和编码上都需要说明 |
| **特殊标记**   | `字源性可拆`             | 独体字余字拆分等机制,不加标记用户会困惑    |

### `/` 占位规则

`/` 表示该字**无需人工撰写理据**--信息已通过编码本身充分传达,再写是冗余。**必须同时满足以下全部条件**才使用 `/`:

1. **前四码唯一**(无同四码字)或**前四码组首**(即空副码字,同组的含副码字已通过副码区分)
2. 部首**视觉主导且无歧义**--位于左侧、清晰可辨,无需额外解释

#### 典型可 `/` 的情形

- 部首在左/上侧,是常见部首,清晰可辨:如 `c`→艹、`k`→口、`m`→木、`s`→纟、`u`→氵、`z`→足/⻊
- 含补码字,且 index.html 已自动标记正字:如 `𫘝 jt2m;.`(正字「駃」自动添加,无需额外理据)

#### 反例(不可 `/`,需要非虚空理据)

- 部首处于非显眼位置(下方、包围内)
- 经过了表外部首处理(简并、代替等)
- 经过了优化分配(部首非按常规字形选取)
- 含副码字,需要指明其前四码组的空副码字

### 理据格式约定

| 情形       | 格式                     | 示例                                  |
| -------- | ---------------------- | ----------------------------------- |
| 占位(无需理据) | `/`                    | `"绷": "/"`、`"沙": "/"`、`"读": "/"`    |
| 空副码合体字   | 部首                     | `"炉": "火"`、`"轨": "车"`、`"油": "水"`    |
| 含副码合体字   | 部首+副码部件(四码→前四码组的空副码码字) | `"汐": "水夕(四码→溪)"`、`"祉": "示止(四码→纸)"` |
| 部首简并     | 部首→简并部首,副码部件(四码→字)     | `"鼐": "鼎→目,乃(四码→柰)"`                |
| 优先标记     | 部首(优先)                 | `"票": "西(优先)"`                      |
| 含补码字     | 补码"部首"                 | `"榦": "补码\"木\""`                    |
| 多音字      | 编码前缀:理据\\n编码前缀:理据      | `"骠": "bc1:马票(四码→标)\\npc4:马"`       |

### 添加前必查

1. **确认编码**:从 `dictionary.txt` 查出该字编码,了解主码(部首)和副码来源
2. **确认是否空副码**:只有四码 → 空副码字,只写部首;五码 → 含副码字,需写明副码部件来源(格式:`部首+副码部件(四码→其前四码组的空副码字)`)
3. **确认是否多音字**:多音字需逐条标注编码前缀
4. **确认是否已有理据**:避免覆盖原有数据(抽查 `dictionary-data.js` 中 `rationale` 对象即可)

### 给 AI 的实操建议

收到用户问"这个字理据怎么写"或"为什么没理据"时:

1. **先查 `dictionary.txt` 确认编码形态**:四码 → `/` 或 部首;五码 → 部首+副码部件+前四码组空副码字
2. **判断是否可 `/`**:前四码唯一且部首视觉主导 → `/`;否则按格式表对应行写
3. **不要塞推导过程、规则术语、输入层影响**--这些不属于理据字段
4. **多音字必须逐条标注**--不能只写一条
5. **怀疑含补码字**:用 `.` 后缀搜索码表确认,再按"补码"部首"格式写

### 「无需理据 / 不查码表」的边界（与 agents.md 对齐）

  推导路径是**默认**的，理据/码表验证是**辅助**的。三件事的分工必须清楚：

| 来源       | 性质   | 何时不需要                                                               |
| -------- | ---- | ------------------------------------------------------------------- |
| **理据**   | 事后解释 | 推导过程本身。理据 = "字形/码表看不出来的信息"，不是输入；占位理据 `/` 的字（绷/沙/读）本就不该读             |
| **记忆文档** | 经验索引 | 字形本身能直接推导时。记忆只讲机制（瘆/晰/膝/晞），不讲每个字——记忆不可能讲完每个字，只抽典型                   |
| **码表**   | 验证工具 | 用户问"应该怎么编"而非"码表里是什么"时（agents.md「开放式回答/合理即可」「你认为是否可以」「多种方案哪种更好」三种场景） |

  **铁律**：**"以查表代替拆字"不可取**。如果看到一个字直接查码表得到 xi1rj 然后回填推导路径，这是码表驱动的归纳而非规则驱动的演绎——遇到码表里没有的字会立刻失语，遇到"为什么"只会复读码表。

  **正确的依赖顺序**（分层而非必备三步）：

```
推导（规则驱动，逻辑必需）
  → 查相关字（前四码竞争者，借力，非必需）
    → 码表验证（核对结果，借力，非必需）
      → 理据（事后解释，借力，非必需）
```

**关键洞察**：「副码优先 = R(c)」（推导完成）与「副码结果 = Code(c)」（码表事实）是**独立的两件事**：

- 问题"副码优先是什么" → 推导直接回答，无需查同组
- 问题"副码结果是什么" → 必须查码表或查同组
- 问题"为什么副码不是优先" → 解释 R'(c) 的递归路径，需要查同组占用关系
- 这三层问题不互相依赖——"查相关字"只对问题 3 有价值，对问题 1、2 都是"借力工具"

**xi1r 组案例的反向教训**：

- 「晞 xi1rp」副码 p 的推导**完全在规则内**就能得出：希 = 巾 + 㐅（康熙部首兜底 + 粗拆分筛掉布/𠂇） → 首选 j 被晰占 → 递归下探到 㐅 → p 行未占 → p
- 不需要读码表 `日㐅(四码→昔，副码j→晰)`，也不需要读理据中的 j→晰 字符串
- 但**仍然需要查同组竞争者**——不查 xi1r 同组，就不知道 j 被晰占，递归就无法启动

## 三、音码规则补充(基于 batch_entry.py)

本节为 `references/rules.md` §二(音码编码规则)的衍生补充。规则本体以 `references/rules.md` §二为准;本节遵循三层流水线:**音韵学正确发音 → 全拼重新形式拆解 → 双拼继承**。`manager/batch_entry.py` 仅与"机械的、一一对应的"部分相关,作为**最后的结果验证**,而非核心并行逻辑。

> **二阶事实(重要)**:下面 3.1 / 3.2 / 3.3 给出的"形式拆解"**同时就是双拼码键位**--双拼是全拼形式拆解的**机械继承**,并不另起一套映射。也就是:"为什么 ya 不写成 oa 而写成 ya"、"为什么 nü 不拆成 nu 而拆成 nü"这类语义问题,与"为什么 ya 不走 o+a 而走 y+a"、"为什么 nü 走 n+ü 双拼码 ny"这类键位问题,**答案同一**--都是按这三条规则的形式拆解。下文例字的"双拼码"列均已实测,详见末尾"实证注"。

### 3.1 零声母的缩小化

**现象**:汉语拼音中存在大量"零声母 + 韵头 + 韵腹 + 韵尾"的音节(如 ya, wai, yue),但 `batch_entry.py` 的 `get_initial()` 对首字符落在 `jqxyw` 的字符串直接返回首字符当声母--这是**形式声母 y / w 的来源**。本条给出判别口诀。

**判别规则**:

- **有介音(韵头)时**:将介音升格为形式声母、把"韵腹 + 韵尾"视作形式韵母。具体映射:i → y,u → w,ü → y(ü 走 3.2 的"ü 单成节 → 简写为 u"链路)。
- **无介音时**:依然当作零声母,标记为 `o`(与 `rules.md` §二一致)。

**例**:

| 字   | 全拼  | 形式拆解     | 双拼码 | 备注                     |
| --- | --- | -------- | --- | ---------------------- |
| 外   | wài | w + ai   | wl  | 介音 u 升格为 w             |
| 牙   | yá  | y + a    | ya  | 介音 i 升格为 y;韵母 a 走 a 键  |
| 月   | yuè | y + ue   | yt  | 介音 ü 升格为 y;韵母 ue 走 t   |
| 爱   | ài  | 零声母 + ai | ol  | 无介音,零声母标记为 o;ai 双拼键位 l |

### 3.2 韵母 ü 的缩小化

**现象**:汉语拼音里能和 ü 组合的声母**只有** j, q, x, n, l 五种--j/q/x 后面的 ü 在全拼中可简写为 u,n/l 后面的 ü **不能**简写。本条同时澄清"ü 在解书双拼里映射到 y 键"的**真实落点**。

**判别规则**:

- **j / q / x 后面的 ü**:全拼层面简写为 u(避免 ju, qu, xu 这种"半拼音形");双拼层面**这个 u 走 u 键**--也就是说 j/q/x 的 ü 不在"ü→y"键位路线上。
- **n / l 后面的 ü**:全拼层面**不能**简写(会与 nu / lu 冲突),保留为 nü / lü;双拼层面**这个 ü 走 y 键**。

**"ü→y"键位的真实落点**:仅限 n/l + ü 这种情形(ny / ly)。它**不等于**"jqxy + u 也走 y 键"。

**例**:

| 字   | 全拼  | 形式拆解        | 双拼码 | 备注                       |
| --- | --- | ----------- | --- | ------------------------ |
| 局   | jú  | j + u(ü 简写) | ju  | jqxy 类:u 是 ü 简写,双拼走 u 键  |
| 女   | nǚ  | n + ü       | ny  | n/l 类:全拼保留 nü,双拼 ü 走 y 键 |

### 3.3 纯介音的双拼化

**现象**:i, u, ü 三者也能单独构成音节(没有声母、也没有韵腹/韵尾)。按 3.1 的口径"有介音即升格为形式声母"--这里"韵头"也升格为形式声母,于是剩下**只剩韵头本身**作为形式韵母。本条把"形式拆分"过程写明。

**判别规则**:纯介音音节 = **形式声母**(i→y, u→w, ü→y)+ **韵头本身**(i, u, u;ü 单成节时按 3.2 简写为 u)。

**例**:

| 字   | 全拼  | 形式拆解                 | 双拼码 | 备注                          |
| --- | --- | -------------------- | --- | --------------------------- |
| 已   | yǐ  | y + i                | yi  | 介音 i 当声母,介音本身当韵母            |
| 无   | wú  | w + u                | wu  | 同上                          |
| 雨   | yǔ  | y + u(ü 按 3.2 简写为 u) | yu  | 嵌套 3.2:ü→u 后,u 仍走 u 键(不是 y) |

### 3.4 与 `rules.md` §二的对应关系(交叉索引)

`manager/batch_entry.py` 的现行逻辑--包括 3.1、3.2、3.3--全部能在代码里机械实现,**不引入额外变量**。这是 `rules.md` §二开篇那句"整个过程是**机械的、一一对应的**,不引入额外变化"的具体兑现。

| `rules.md` §二原文摘录                                      | 代码 / 本节规则对应                                                                                                                   |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 「零声母:a, o, e→o。全拼中不存在以 i, u, ü 开头的拼音, 分别视为声母 y, w, y。」 | **3.1 零声母的缩小化**--"不存在的拼音 → 视为 y, w, y" 就是把介音升格为形式声母。                                                                          |
| 「uai/ü→y (声母 jqxy 的, ü→u)」                             | **3.2 韵母 ü 的缩小化**--括号内 "声母 jqxy 的, ü→u" 是 j/q/x 分支(此时双拼键位就是 u,并非 y);n/l 分支在 §二原句没出现,但同样由 3.2 兜底--**这是"ü→y"键位的真正落点**(ny / ly)。 |

> 表外的约定(如 3.3 纯介音单成节)本质上是 3.1 的边界情形,但因现行 `rules.md` §二未举出单音节例子,单列一条便于解释。

### 3.5 实证注:双拼键位 ≈ 形式拆解

本节"双拼码"列已用 `manager.batch_entry.hanzi_to_abc` 实测验证。关键点:

- **形式声母 + 形式韵母** 就是双拼键位(或其直接继承)。双拼不另起一套独立映射,键位是形式拆解的**机械延续**。
- 因此,「ü→y」只在韵母位独立出现的那个 ü(即 ny / ly)落 y 键--因为 nü 的形式拆解就是 n + ü,规则 2 给出双拼键位就是 ny。
- **实测即结果**:`hanzi_to_abc` 直接产出最终双拼键(如 `wl4 / ya2 / yt4 / ol4 / ju2 / ny3 / yi3 / wu2 / yu3`),与 §三 表格"双拼码"列一一对应:**单 a 走 a 键(牙 = ya)**、**ai 走 l 键(爱 = ol)**-- §二 韵母表里 `a→a / ai→l` 是两行,不是同一行。
- 9 个例字实测全部与 §三 预测一致:外 wl / 牙 ya / 月 yt / 爱 ol / 局 ju / 女 ny / 已 yi / 无 wu / 雨 yu(声调位以实测为准)。
- `batch_entry.py` 在这里**仅起验证作用**——它的输出与 3.1 / 3.2 / 3.3 的形式拆解完全一致，是因为后者已经把双拼层的工作做完；代码的"机械性"正好是用来交叉确认"形式拆解与双拼键位一致"的工具。

## 四、含繁体字词语的编码策略（基于 ciyu_ops.py）

### 现象：功能8"添加词语"对繁体词的处理

`manager/ciyu_ops.py` 中的 `ciyumain()` → `process_two_char_word()` / `process_multi_char_word()` 在生成词语编码后，会检测组成字的单字编码是否含 `.`（补码标记），若有则在整词编码末尾统一追加 `.`。

### 核心原则：单字繁体标记 → 整词继承

**一个词只要任意一个字是繁体（单字编码含 `.`），整词就带 `.`。**

这跟补码规则一脉相承——`.` 是"繁异标记"，单字有 `.`，由这些字组成的词也要有 `.`。不区分"词中一两个字是繁体、其余是简体"的中间态：整词的编码形态只分"全简体"（无 `.`）和"含繁体"（有 `.`）。

### 两阶段处理

#### 阶段一：检测（`has_dot_in_codes`）

```python
def has_dot_in_codes(*codes):
    return any('.' in c for c in codes if c)
```

在用户选完每个字的具体读音之后，遍历已选编码，**任意一个**含 `.` 即判定为繁体词。

判定时机在读音选定之后，不在"码表查询"阶段——因为一个字可能在 `dictionary.txt` 中有多条记录（简体 + 繁体），用户选哪个读音才决定了最终用的是简体编码还是繁体编码。

#### 阶段二：追加（`append_dot_to_code`）

- **二字词**：`generate_all_combinations` 生成全部候选组合后，每个组合直接 `+ "."`。用户从这些带点组合中选一个。
- **三字及以上词**：`generate_default_codes_for_word` 生成默认编码后，通过 `append_dot_to_code` 在末尾补 `.`。若默认编码含空格（两个变体，如四字词方案1和方案2），两段**分别**补 `.`。用户可接受默认或自行输入。

`append_dot_to_code` 有防御性设计：若末尾已有 `.` 则不重复追加；含空格时逐段判断。

### `.` 的位置与语义

| 层级  | 编码形态                | `.` 的含义                                    |
| --- | ------------------- | ------------------------------------------ |
| 单字  | `ABCDF` 或 `ABCDE.F` | `.F` 在第五位之后，标记繁异具体形式（`.f`=大陆繁体、`.g`=港澳异体等） |
| 词语  | `...` + `.`         | `.` 在编码最末尾，仅标记"整词含繁体"，**不细分**是哪一套繁体标准      |

区别原因：词语编码生成的第一原则是**实用**——用户不需要为"一个词里三个字各自属于哪套繁体"操心。`.` 在词尾就是开关语义：这个词得用繁体来理解。

### 前端匹配

词语查询走 `query_phrase`（`ciyu.txt` 精确匹配），**不是** `query_by_prefix`（`query_by_prefix` 只读 `dictionary.txt` 处理单字，其中 `.F` 是单字补码后缀，与词语编码无关）。

`query_phrase` 是简单精确匹配——用户输入的编码串必须在 `ciyu.txt` 某行的编码列表中完全命中。因为词语编码末尾有 `.`（如 `gojw.`），用户输入 `gojw.` 才能被 `query_phrase` 精确命中「國家」。

但实际输入流程中，词语查询由前端 `_on_input_change` 驱动：连续编码在提交前（空格或自动上字触发）会调用 `query_phrase`。如果用户一直打到底（打完 `gojw` 立刻空格），这段编码串就是 `gojw`，`query_phrase` 不会命中 `gojw.`。用户需要把 `.` 也打进去（`gojw.`），或者等前端在候选列表里展示——但候选列表来源于 `query_by_prefix`（单字），不涉及词语。

**这意味着：`. ` 在词语中是一个必须主动打入的编码字符。** 用户需要知道这个词是繁体词、需要敲 `.` 才能走 `query_phrase` 命中，不能指望省略 `.` 还能匹配。

### 零重码保证

`.` 是一个属于 `CODE_CHARS` 的合法编码字符，单字补码中已用于全局零重码。词语层面，`. ` 在末尾同样把繁体词和对应简体词（如果存在）隔到不同编码空间——`國家 gojw.` 与 `国家 gojw`不会重码，因为 `query_phrase` 的精确匹配不会把 `gojw.` 和 `gojw` 视为同一编码。

### 与补码规则的承接关系

词尾 `.` 直接延续了单字补码（`rules.md` §六）的"第一繁体"概念：

- 单字：`.` 直接表示"该字在常用语境下的第一繁体"（如「纪」→「紀」编码 `ji4s.`）
- 若单字对应多个繁体、需要区分，才用复合后缀：`.f`（大陆繁体）、`.g`（港澳异体）、`.t`（台湾异体）、`.j`（日本汉字）等
- 词语：`.` 在末尾统一标记"整词含繁体"——这些单字的繁体/异体选择**已经在单字编码选读音时由用户确定**，词尾 `.` 不再细分

当词中含补码通配`.j` 字或其他复合后缀的单字时，词尾同样追加 `.`（`has_dot_in_codes` 只判断 `'.' in c`，不区分子后缀类型）。

### 实操建议

1. 用户添加繁体词时，管理工具会自动检测并提示"（检测到繁体字，编码末尾已加 .）"，无需手动操作。
2. 审查 `ciyu.txt` 时，遇到末尾带 `.` 的词条，可反查组成字的编码确认哪些字是繁体。
3. 用户问"为什么 X 繁体词编码末尾有 ."时，答：因为词里 `N` 个字是繁体（逐一指明），按规则整词末尾统一加 `.`。

## 五、字统网辅助（基于 zi-tool-lookup 技能）

字统网（zi.tools）提供字典字源、Unicode 字符库、康熙部首三源对照的客观字料。

**核心原则**：字统网是事实查询工具，不是编码决策工具——它给事实（IDS 分解、Unicode 码位、康熙部首、读音、义项、字形演化、异体关系），不给决策（解书编码、部首码分配、多音取舍、异体补码路线、码表收录）。其输出永远要过一道解书规则+记忆+码表的判断。

### 三大功能

| 功能   | 用于                           | 查什么                                                                                             |
| ---- | ---------------------------- | ----------------------------------------------------------------------------------------------- |
| 辅助决策 | 读音取舍、部首归属、独体/合体、余字拆分、副码常用度   | 官话读音+义项主次（常用度信号，配合 05「冷僻读音可放弃」）；IDS 分解+康熙「X部X畫」（部首归属、结构判断）；字形演化图（视觉，需截图）；异体图谱（剔除为其他字借用的读音，参 02） |
| 识别边界 | 罕用字、扩展区、简繁关系                 | 收录边界：基本平面为主，扩展 A 部分收录，扩展 B 及以远/PUA 不录，IVS 不引入；简繁为独立码位→补码路线（参 02），同一码位多音→各自独立编码                  |
| 纠正错误 | AI 部首归属简化、字源拍脑袋、多音简化、结构拆分视觉化 | 三源（字典字源/Unicode 字符库/康熙部首）交叉验证暴露单源盲区；标「构形不明」时诚实承认，不擅自补字源说解                                       |

### 字例：「乇」的字形纠错

AI 易误判为「丩 + 一」（实际上应该是`⿱丿七`），字统网给出的字形事实：

- 该字归**丿部**，字符集索引直接标 G 部件码 0370「乇/托字边」——214 部首之外的扩展部首，只看楷书字形容易漏检；
- 甲骨文中「乇」与「力」形近（横在上 vs 横在下），仅看楷书看不见这层关系；
- 学界对其字源标「构形不明」——此时不擅自补说解。

## 六、长通用符号的编码探索

> 本节为探索性规则，暂未写入 rules.md。rules.md 保持稳定，探索中的编码规则先在 memory 沉淀，待规则成熟稳定后再考虑升格。

### 边界：什么算"长通用符号"

目前词语表中的长通用符号（长度 > 1、每一位均为符号）仅有**成对标点**这一类，如「」（）、《》【】“”。**混合汉字的词不属于通用符号**，仍走正常"多字词"逻辑（按字数拆分编码）。

判定边界与查询工具 `index.html` 的 `getPhraseRationale` 一致：借用 `isHanzi` 对词语逐位检测，**所有位均非汉字**时判为通用符号，编码拆成「首码 + 后续码位」；**只要含任意一位汉字**，就走多字词逻辑。

### 编码方案：类型符 + 标点名 + 两个方向

成对标点的编码 = **类型符 + 标点名 + 左方向 + 右方向**，共四码。

以「」（`djzy`）为例：

| 码位  | 字母  | 含义            |
| --- | --- | ------------- |
| 1   | d   | 类型符（点，中文标点前缀） |
| 2   | j   | 标点名（角，直角引号）   |
| 3   | z   | 左方向（左符「）      |
| 4   | y   | 右方向（右符」）      |

它可理解为左符「（`djz` = 点+角+左）与右符」（`djy` = 点+角+右）的拼合：共享的「类型符 + 标点名」`dj` 只写一次，再接左方向 `z` 与右方向 `y`，得 `djzy`。

当前码表收录的成对标点（类型符恒为 `d`、左方向恒为 `z`、右方向恒为 `y`，仅标点名码位不同）：

| 成对符号 | 编码   | 标点名  | 左符    | 右符    |
| ---- | ---- | ---- | ----- | ----- |
| 「」   | djzy | j（角） | 「 djz | 」 djy |
| （）   | dkzy | k（括） | （ dkz | ） dky |
| 《》   | duzy | u（书） | 《 duz | 》 duy |
| 【】   | dvzy | v（中） | 【 dvz | 】 dvy |
| “”   | dyzy | y（引） | “ dyz | ” dyy |

### 立词性：与顺势原则的张力

「立词必要性判断」章节已说明：**可由更小基础词（或符）组成的词，不推荐重复立词**（顺势输入优先）。按此原则，成对标点本可由左符 + 右符顺势连打得出，似乎不必单独立词。

但某些通用符号由于**经常联合出现**（成对标点天然成对、高频连用），为其立词能带来真实的输入效率收益，因此仍需保留其立词可能。这是顺势原则在符号域的一个补充/例外。

### 适用范围

目前该规则**仅适用于成对标点**；其它类型长通用符号的编码规则仍在探索中，暂不推广。
