## 四、前端简打机制

### 底层五大机制

前端简打体验由五个独立机制协同实现。理解它们的职责边界和时序关系，是分析一切输入场景的前提。

#### 码表排序（离线·决策层）

`process_file()` 在整理阶段一次性排好 `dictionary.txt` 的物理行顺序：

- **一级简码置顶**：`first_level_map` 的 24 个字（如「我」wo3g）在各自首字母分组内强制排第一，不是创建独立短编码，而是干预排序位置
- **char_priority 排序**：数字去0加"."（1-9, .）< 字母加0（0, a-z）< 分号（;），使短码、数字码自然排在长码、含特殊字符码前面
- **效果**：查询时不需要任何运行时排序或频率计算，`startswith` 线性扫描的第一个匹配即最优选

#### 前缀匹配（在线·查询层）

`query_by_prefix()` 纯 `code.startswith(prefix)` 线性扫描，返回汉字 + 剩余编码：

- **输入级简码**：因排序把最短编码排第一，二码前缀（如 `uu`→书 uu11）自动定位最常用字，无需人工指定
- **全前缀链贯通**：一级简码是排序干预，所以「我」在 w/wo/wo3/wo3g 所有前缀深度都排第一——打一位、两位、三位、四位所见皆「我」
- **副码 a 占空**：输入第 5 位 a 时，只匹配四码无副码的常用字
- **补码穿透**：前缀命中补码 `.` 前的编码(且未自动上字)时，显示 `.` 作为剩余编码提示

**前缀匹配 ≠ 全码**。一段编码被前缀匹配命中，不等于它打全了四码。要逐段对照 ABCDE 看填到了哪一位：

- `y;` → 仅 AB（声韵），C 缺 → 前缀命中「英」
- `wf2` → ABC（声韵调），D 缺 → 前缀命中「文」
- `ci2y` → ABCD，全码 → 精确命中「词」

未打全也能上屏，是因为离线排序把最常用字推到了该前缀组的第一位。

#### 自动拆分（在线·调度层）

`split_sequence()` 纯字符串特征判断，不查码表，五条件递归执行：

| 条件  | 触发              | 切割         | 盲区              |
| --- | --------------- | ---------- | --------------- |
| 1   | 无数字 + len > 2   | 每 2 位切     | 含数字的段（无帮助）      |
| 2   | 数字在索引 **> 2**   | 往前 2 位切    | 数字在索引 ≤ 2（无需拆分） |
| 3   | 连续两个数字+无 `.`    | 第二个后切      | 合体字（不存在连续两个数字）  |
| 4   | len > 5 + 无 `.` | 第 5 位后切    | 4位及以下字          |
| 5   | `.` 后 len > 1   | `.` 后 2 位切 | 无 `.` 的段        |

**盲区核心**：条件 2 的 `index > 2`——只能做到往前拆分，不能往后预测。这是理解单字场景 (1)(2)(3)(5) 的关键。

多字预览：`query_multi_chars()` 取各部件第一候选首字拼接，打之前就能看到结果。

#### 自动上字（在线·决策层）

`auto_commit` 在前缀匹配结果中实时判定：当前缀长度 ≥ 4 且候选列表仅有一个时，自动上屏，无需用户按空格。

- **触发条件**：`len(prefix) ≥ 4` 且 `len(candidates) == 1`
- **执行时机**：逐字符实时判定，在 split 之前执行
- **CLI 行为**：CLI 模拟前端写死 `auto_commit = "1"`（始终开启）；真实前端 `ime.py` 可通过设置面板关闭

**与输入场景的关系**：

| 场景        | 自动上字行为            |
| --------- | ----------------- |
| (4) 四码唯一  | 直接上屏，后续编码进入独立单字模式 |
| (5) 四码不唯一 | 不触发，候选列表显示副码等待选择  |
| (6) 五码全码  | 直接上屏（零重码保证唯一）     |

**auto-commit 抢断风险**：场景 (5) 中，若候选不唯一且第二字初码恰好与某候选副码重合，连续输入时 auto-commit 会抢在用户意图之前把错误字上屏（如 `yi4r + w → yi4rw` 唯一命中「易」→ 抢断）。这是 auto-commit 的唯一反模式，解决方案是声明边界（空格 / `'` / 输入 a 占空）。

#### 优先上词（在线·调度层）

当进入多字模式后，空格提交时如果存在词语候选且「优先上词」设置开启，优先上屏词语而非逐字首选组合。

##### 匹配方式：完全匹配，非前缀匹配

`query_phrase()` 使用 `code in parts[1:]` 进行**完全相等判断**，与单字查询的 `startswith` 前缀匹配是两套不同的查询逻辑。

- 一个词语在 `ciyu.txt` 中可以注册多个编码（如 `那些 naxx`），只有`query_phrase("naxx")` 命中
- 但 `query_phrase("n")` 不命中——因为 `"n"` 不在词语的编码列表里
- 这意味着词语没有"简码"概念：不存在"打短码自动候选多个词"的情况，只命中精确注册的编码

##### 两种查询模式

词语查询在运行时分为两种独立触发路径，且不受自动拆分结果影响：

| 模式            | 触发条件                           | 查询方式                                                                     | 示例                                                                                                     |
| ------------- | ------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **整段查询**      | 多字模式 + 输入串中**无单引号**            | 将整个 `processed` 传递给 `query_phrase()`，整体匹配                                | `update_display()` 中：`query_type == "multi_part" and "'" not in processed` → `query_phrase(processed)` |
| **人工单引号分段查询** | 多字模式 + 输入串中**有人工单引号** + 优先上词开启 | `get_phrase_segments()` 按 `'` 切段后，对每段 `len ≥ 3` 逐一调用 `query_phrase(seg)` | 用户输入 `qiui'naxx` → `query_phrase("naxx")` 命中「那些」                                                       |

**整段查询**的前提是已经进入多字模式——即 split 已切出多段。单字模式下即使输入恰好等于词语编码，`update_display()` 也不会触发 `query_phrase()`。

**单引号分段查询**中，长度 < 3 的段不查词语（直接走自动拆分取首选字）。只有 ≥ 3 位的段才尝试 `query_phrase`，未命中则降级到自动拆分取首选字。

- **触发条件**：多字模式 + 两种查询模式 + `query_phrase()` 有匹配 + 优先上词开启
- **设置控制**：`ime.py` 底部状态栏「优先上词」按钮（绿色 = 开启，红色 = 关闭）。关闭时空格上屏逐字首选组合
- **快捷上词**：按 `!` 直接上屏词语候选，不受优先上词开关影响
- **与单字管线的隔离**：优先上词只在多字模式阶段参与决策，单字输入流程不受其影响

#### 五大机制协同

五者时序：**auto-commit（自动上字）先于 split（自动拆分）**，自动上字仅在单字阶段生效，一旦通过自动拆分或单引号进入多字模式便不再生效。多字模式下，如果输入的字符串中没有单引号，则只会将整段作为整体查询词语，不涉及内部拆分，如果人工输入了单引号，则会尝试根据人工声明结果的每段查词语。auto-commit 逐字符实时判定（当前缀 ≥ 4 码且唯一候选 → 直接上屏），split 会在输入内容变化时对"还活着的多字串"做切割，优先上词在 split 切出多段或输入单引号后决定上词还是上字。

| 机制   | 函数                    | 执行时机       | 本质            |
| ---- | --------------------- | ---------- | ------------- |
| 码表排序 | `process_file()`      | 离线，一次      | 排序即频率表        |
| 前缀匹配 | `query_by_prefix()`   | 在线，每击键     | startswith 扫描 |
| 自动上字 | `main_function()`内联逻辑 | 在线，每击键（单字） | 四码唯一即上屏       |
| 自动拆分 | `split_sequence()`    | 在线，每击键（多字） | 五条件机械切割       |
| 优先上词 | `query_phrase()`      | 在线，每击键（多字） | 完全匹配，多字模式优先上词 |

协同效果：「不用背，打就完事了」——排序让短码优先，前缀匹配让未打全也能命中，自动上字让常用字免空格直达，自动拆分让连续编码无需人工切字，优先上词让多字词一键上屏。

### 单字输入场景（向后分隔）

以下六种场景覆盖单字编码的所有边界情况。核心判断依据：**打完当前字的前 N 码后，能否直接打第二字编码而不被 auto-commit 抢断、不被 split 误切。**

#### (1) 单字 1 码锁定（一级简码）

24 个字（w→我、n→你 等），无数字。五大条件全部失明。

- **直接打第二字编码**：依靠第二字调码定位。合并串中第二字调码在索引 ≥ 3，触发条件 2 往前 2 位切。
  
  ```
  w + ye3 = "wye3"  → C2: 数字 3 在 index 3(>2) → 往前 2 位 → "w" + "ye3" ✓
  w + jm4j = "wjm4j" → C2: 数字 4 在 index 3(>2) → 往前 2 位 → "w" + "jm4j" ✓
  ```

- **直接空格上屏**：保守且正确的退路。

- **两个 1 码连打**：符合下文 2(1)——1 码锁定字跟在小于五位的非独体字编码后，需要拆分。必须空格或 `'`。
  
  ```
  w + n = "wn" → 无数字，len=2，不 >2 → C1 不触发。其余全失效 → 不拆分。
  正确: w n（空格分隔）
  ```

#### (2) 单字 2 码锁定

无数字，但合并串中第二字编码决定了拆分方式：

- **与另一1或2 码连打**：C1（无数字 + len>2 → 每 2 位切）直接处理。（2(1)也有表述）
  
  ```
  na + yi = "nayi" → C1: len=4>2 → 每 2 位切 → "na"+"yi" ✓
  nr + n = "nrn" → C1: len=3>2 → 每 2 位切 → "nr"+"n" ✓
  ```

- **第二字 ≥ 3 码（含调码）**：合并串第一个数字在 index ≥ 3，C2 锚定。
  
  ```
  na + ye3  = "naye3"  → C2: 数字 3 在 index 4(>2) → 往前 2 位 → "na"+"ye3"  ✓
  na + hg2w = "nahg2w" → C2: 数字 2 在 index 4(>2) → 往前 2 位 → "na"+"hg2w" ✓
  ```

- **直接空格上屏**：保守退路。

#### (3) 单字 3 码锁定

3 码 = ABC（如 ye3→也）。数字在 index 2，恰好 `index ≤ 2`——条件 2 盲区。直接连打的合并串不会被自动拆分。**不可直接打第二字编码，必须先观察候选。**

候选列表返回所有剩余编码（含主码 D 和副码 E）。判断流程：

```
打完 3 码，候选显示各字的剩余编码。

1. 第二字初码是否命中候选列表中某个主码（D 位）？
   └─ 是 → 进入步骤 2
   └─ 否 → 判定该主码无字 → 可以直接打第二字编码，依靠第二字调码定位

2. 该主码下有几个字？
   ├─ 仅 1 字 → 必须声明边界（空格或 '）
   └─ >1 字  → 进入步骤 3

3. 第二字韵码（合并串第 4 位）是否与候选列表中某个副码（E 位）重合？
   └─ 是 → 必须声明边界（空格或 '）
   └─ 否 → 可以直接打第二字编码，无需声明边界
```

示例：

```
打完 "ba1"，候选: 釟(j) 吧(k) 叭(kb) 粑(m) 朳(mb)...

第二字初码 = "d" → ba1d
  b 不命中任何主码 → 该主码无字 → 可直接连打，靠调码定位

第二字初码 = "k" → ba1k
  k 命中主码 → 主码 r 下有「吧」「叭」两字（>1）
  → 第二字韵码 = ba1k[?]  继续判断
  假设第二字编码为 "kl14" → ba1k + l14 → 合并串 "ba1kl14"
  kl14 的韵码 = l，候选副码中吧(空)、叭(b) → i 不命中副码 → 可直接连打
  合并串第一个数字：1 在 index 5(>2) → C2 锚定 → "ba1"+"kl14" ✓
```

**核心结论**：3 码锁定场景下，保守做法是用空格封口。但理解冲突判断后，很多情况可以省掉这个空格。

#### (4) 单字 4 码锁定并自动上字

前四码唯一 → auto-commit 直接上屏 → 光标移到字后，后续编码进入独立的单字模式。**直接打第二字编码，无需考虑已上屏的第一字。**

#### (5) 单字 4 码锁定但没有自动上字

前四码不唯一 → auto-commit 不触发。候选列表显示各字的剩余编码（副码 E 或空）。

**判断流程**：

```
观察候选中的副码（E 位）是否与第二字初码重合：
  └─ 重合 → 必须声明边界（空格 / ' / 输入 a）
  └─ 不重合 → 可以直接打第二字编码，依靠第二字调码定位
```

**边界声明的特殊方式——输入 a**：`yi4ra` 里 a 触发占空副码逻辑（`len≥5 且 prefix[4]=='a'`），精确匹配 `yi4r`，忽略 a——锁定「亿」。a 在声明："我的编码在 E 位是空的，后面没有东西了。"

**不重合时为什么可以直接打**：第二字调码一旦出现，C2 锚定会抢在 C4 之前触发，拆分正确：

```
yi4r + wo3 → yi4rwo3 → 数字 3(index 6)触发 C2 → yi4r + wo3 ✓
```

**重合时必须声明边界**：第二字初码恰好是某个候选的副码，此时：

- 威胁 ：auto-commit 抢断——`yi4r + w` → `yi4rw` 唯一命中「易」→ 上屏错误

#### (6) 单字 5 码锁定

5 码 = ABCDE，全码精确命中，必然唯一（码表零重码保证）。auto-commit 直接上屏。**直接打第二字编码，后续进入新的单字模式，无需考虑已上屏的第一字。**

---

#### 进入多字模式的方式

场景 (1)(2)(3)(5) 的结果都可能进入多字模式。多字模式有两种进入方式：

1. **不经声明边界，通过自动拆分自然进入**：当两个字之间的边界恰好被 split 五条件之一覆盖时，用户不需要做任何事，split 就切出了两个编码段 → 多字模式
2. **通过单引号 `'` 显式声明进入**：当自动拆分五条件全部盲视时，`'` 画出边界 → 多字模式

空格是"提交动作"而非"模式入口"——空格把前面的编码段对应的汉字直接上屏，不涉及具体切割。

**一旦进入多字模式，就无需再警惕自动上字**，直接根据拆分规则输入编码即可。

---

### 多字模式中的简打取舍（向前分隔）

为了输入更短的编码，可能无法满足自动拆分边界，需要人工声明（空格或单引号）。

#### 2(1) 简短编码后的拆分需求

单字 1 码或 2 码锁定的，跟在小于五位的非独体字编码或小于四位的独体字编码（且编码不等于两位）后：**需要拆分**。

原因：1 码和 2 码均无数字，split 五条件对它们盲视。当它们跟在其他编码后面时，合并后的编码串在 C2 找不到锚点（除非后续编码含调），在 C4 也找不到切割点（除非总长 >5 且前字 ≥4 码）。如果前段编码为两位，可根据C1实现自动拆分，无需人工再拆分。

```
yi4r + na → yi4rna  → C4: len=6>5 → 第 5 位切 → yi4rn+a → 错误
正确: yi4r na（空格分隔）或 yi4r'na（单引号分隔）
```

#### 2(2) 词语编码的拆分需求

词语编码（如 naxx→那些）不涉及自动拆分。

- **词语编码跟在任意编码串后**：需要拆分，否则无法识别词语前边界
- **任意编码串跟在词语编码后**：需要拆分，否则无法识别词语后边界

```
qiui + naxx → qiuinaxx → C1: 每两位切 → qi'ui'na'xx → 查不到词
正确: qiui'naxx
```

#### 2(3) 统一自动上字场景的边界声明

在编码串撰写过程中，如果场景 1(4)（4 码锁定并自动上字）或 1(6)（5 码锁定）中紧接着出现 2(1) 或 2(2) 的情况——即前字已被 auto-commit 上屏，后字编码段恰好属于需要拆分才能独立识别的类型——需要在纯字符串中模拟"自动上字"现象：**用显式边界声明来达到和 auto-commit 相同的切分效果**。这不是插入空格，而是用字符串级的边界标记（`'` 或空格）告诉 split："这里已经是另一个字了。"

---

#### 2(4) 首选字避让词语

逐字编码拼接后，形成的编码串可能恰好命中一个**其他词语**的注册编码。此时 `query_phrase` 返回的是该词语，而非用户意图的逐字组合——这就是"首选字被词语抢断"。

**示例**：

| 意图  | 逐字编码        | 拼接码     | 冲突词 | 结果             |
| --- | ----------- | ------- | --- | -------------- |
| 千眠  | qm + mm     | `qmmm`  | 前面  | 逐字拼接意外命中词语"前面" |
| 书茹发 | uu + ru + f | `uuruf` | 输入法 | 同上             |

**冲突本质**：不是 `split_sequence` 拆分错误，也不是自动上字误触——而是整段编码本身恰好等于另一个词语的注册编码，导致 `query_phrase` 返回该词而非逐字首选组合。

**解决方式（两种）**：

1. **加码区分**：再补一位编码，如 `qmmm` → `qmmm2`。这增加了码长，且可能引入新的词语冲突。
2. **分隔避让**：在两字中间分隔，如 `qmmm` → `qm mm`。牺牲了流畅性，但保证无冲突。

由于简打机制追求**最短编码**而非最流畅编码，选择**方案 2：分隔避让**。

**分隔算法**（贪心回退）：

```
1. 检测拼接码是否命中某个 ≠ 意图文本的词语
2. 若是 → 尝试将末字编码与前面编码分开（如 uuru f）
3. 若分开后剩余合并段仍有词语冲突 → 前移分隔位置（如 uu ruf）
4. 重复，直到无冲突
5. 若所有位置均有冲突 → 每字之间全部分隔（如 uu ru f），一定成功
```

核心思想：逐字编码拼接是"默认粘连"，但粘连不能以引入错误词语为代价。当一个拼接串"看起来"像另一个词时，必须用空格声明："这里不是那个词，是几个独立的字。"

**反向视角**：本节讲碰撞发生后用户侧如何避让；立词阶段存在对称的反向规则——候选词最简码需避让高频首选字组合的码位（如 `viyi` 保留给 之+一，质疑、执意改用长码），见记忆文档 06「立词必要性判断 · 原则 4」。

### 单引号 `'` 的统一表述

`'` 的唯一目的：**在自动拆分五大条件全部失效的地方，人工画出编码段边界。**

`'` 介入当且仅当自动拆分无法在两个编码段之间画出边界。按简码级别分类：

**一级简码（1 位）**：无数字，五大条件全部失明。前后都需要 `'`。（2(1)）

- `ye3'b` → `ye3b` 视作一字四码，`3` 在索引 2 ≤ 2，条件 2 不触发

**二级简码（2 位）**：无数字，五大条件全部失明。前面需要 `'`。（2(1)）

- `na`（那）→ 前面有编码时，如 `jx1u'napg2yyb3k`，无 `'` 则 `una` 被当连续编码

**三级简码（3 位 ABC）**：数字在索引 2，恰好 `index ≤ 2`——条件 2 盲区。后面需要 `'`。（1(3)）

- `ye3` → `ye3b`，条件 2 判 `3` 在索引 2 不触发，整体被当一字四码查 `ye3b`。必须 `ye3'b`

**四级简码（4 位 ABCD）**：同三级，数字在索引 2，盲区。后面需要 `'`。（1(5)）

- `jm4j`（建）→ 同上

**方向性规律**：

- 一级/二级：对**前**分隔（后面的编码找不到自己的音码起点）
- 三级/四级：对**后**分隔（后一字的音码被前一字吞为主码/副码的一部分）

**词语分隔是同一原理的特例**：`query_phrase` 之所以需要 `'`，是因为两个注册词之间的边界本身就不会经过自动拆分（代码不拆）。本质仍然是：两个独立查询单元之间没有自动拆分条件能识别。（2(2)）

**实例复盘**：

| 编码串               | 盲区级别               | 方向        |
| ----------------- | ------------------ | --------- |
| `jx1u'napg2yyb3k` | na=二级（前）           | 被前段吞没     |
| `jm4j'jp1d`       | jm4j=四级（后）         | 后字音码被前段吞没 |
| `ye3'b`           | b=一级（前）+ ye3=三级（后） | 双向盲区      |
| `qiui'naxx`       | naxx=注册词（前）        | 词语显式拆分    |

### 边界声明的三种方式

前缀匹配让用户"没打全就能上屏"，代价是"系统不确定你打没打完"。这不是设计缺陷——这是便利本身的价格标签。用户省掉的信息（字边界），总要在某个环节补回来。

**三层边界感知机制**（从隐到显）：

1. **候选列表** → 当候选不唯一时，列表本身就是"这里可能有边界"的提示信号。用户看到多个候选，自然的反应是"先把这个字搞定，再考虑下一个"——隐性边界感知
2. **自动上字** → 当 `len>3 且唯一候选` 时，程序替用户做上屏决策。仅在用户无视候选列表提示、继续往下敲、且延伸出的唯一候选不是目标字时才会出错
3. **显式分隔符（空格 / `'` / 关闭自动上字）** → 在自动上字和候选列表都不够用时，由用户主动声明边界

三者不是竞争关系，而是互补关系。候选列表降低了对显式分隔符的需求，自动上字降低了对候选列表的依赖，空格和 `'` 兜底剩余的模糊地带。

**三种声明方式（前端全部支持）**：

| 方式    | 操作                   | 代价        | 适用范围        |
| ----- | -------------------- | --------- | ----------- |
| 空格    | `yi4r` → 空格 → `wo3g` | 自然节奏，一瞬停顿 | 日常最常用       |
| `'`   | `yi4r'wo3g`          | 多一个符号键    | 精确控制，连续高速输入 |
| 关自动上字 | 设置里关掉                | 每个字多一次确认  | 不信任任何自动决策时  |

ai无法用 CLI 关自动上字（CLI 写死 `"1"`），但真实前端 `ime.py` 支持设置面板开关——三种全部可用。

### 教学案例：「滚滚长江东逝水」

#### 新手策略

逐字输入，每个字上屏后再打下一个，不贸然组合。

**新手版**：`gp3u gp3u ih24 jd1u ds14 ui4zv uv36`（7 段，29 码，逐字四/五码打全，确定性最高）

- 每个字打全编码（四码或五码），确定性最高
- 无需理解 auto-commit 和 split 的任何内部机制
- 顺便学习每个字的完整编码

#### 进阶策略

在理解两层机制的前提下，以最少的空格和最短的总码长应对所有边界。

**高阶版**：`gp3ugp3uih2 jd1u dsui4zvuv3`（3 段，25 码）

逐字分析：

| 字   | 高阶输入         | 策略                                                                                    |
| --- | ------------ | ------------------------------------------------------------------------------------- |
| 滚滚  | `gp3ugp3u`   | 四码唯一 auto-commit，无空格                                                                  |
| 长   | `ih2` + 空格   | 场景1(3)：前缀未闭，`j` 被「常」抢断 → 封口                                                           |
| 江   | `jd1u` + 空格  | 场景 2(1)： 后字 ds 无调码 C2 风险 → 封口                                                         |
| 东逝水 | `dsui4zvuv3` | `ds` 两码无数字 → C1/C2 不切；`ui4zv` 五码含数字 → C2 +C4锚定；`uv3` 三码含数字 → 独立成段。三子段各靠不同条件正确拆分，零人工空格 |

新手版是**学编码**，高阶版是**学系统**。高阶版的每一次省略都是对某条边界规则的主动利用。

### 六大宣传锚点

1. **不背简码表，简码自然来** — 输入级简码自动涌现
2. **打一串编码，出一句话** — 多字连续输入 + 实时预览

### 教学案例：《半壶纱》副歌六句

对整段副歌 48 个汉字的完整简打分析，验证所有简打机制在实际歌词输入中的表现。

#### 副歌原文与编码

| 句     | 原文        | 简打编码                            | 字数     | 输入字符    | 全码字符    | 省            |
| ----- | --------- | ------------------------------- | ------ | ------- | ------- | ------------ |
| 1     | 倘若我心中的山水  | `th3r row xnvsd ujuv3`          | 8      | 21      | 32      | 11           |
| 2     | 你眼中都看到    | `nyj3m vsdbkj4dk4`              | 6      | 15      | 24      | 9            |
| 3     | 我便一步一莲花祈祷 | `wbm4r yibu4v yilmhw qidk3`     | 10     | 28      | 40      | 14           |
| 4     | 怎知那浮生一片草  | `zfvi1u nafu2uvugyipmck3`       | 8      | 25      | 33      | 9            |
| 5     | 岁月催人老     | `sv4uyt4jcv1r rlk3l`            | 7      | 17      | 28      | 5            |
| 6     | 风月花鸟一笑尘缘了 | `fg1pyt4j hwncyixc4zif2tyr2s l` | 9      | 31      | 36      | 8            |
| **计** |           |                                 | **48** | **137** | **193** | **56** (29%) |

全副歌输入 137 字符，对比全码 193 字符，省掉 29%。拆开看省码来源：

| 机制        | 字数  | 占比    | 代表字                                                                                                              |
| --------- | --- | ----- | ---------------------------------------------------------------------------------------------------------------- |
| 一级简码（1码）  | 6   | 12.5% | 我(w)、你(n)、的(d)、人(r)、了(l)                                                                                         |
| AB 二码简码   | 21  | 43.8% | 若(ro)、心(xn)、中(vs)、山(uj)、都(db)、一(yi)、莲(lm)、花(hw)、那(na)、生(ug)、片(pm)、鸟(nc)、怎(zf)                                    |
| ABC 三码简码  | 4   | 8.3%  | 水(uv3)、看(kj4)、到(dk4)、草(ck3)                                                                                      |
| 词组匹配      | 2   | 4.2%  | 祈祷(qidk3)                                                                                                        |
| 四码全码（不可省） | 15  | 31.3% | 倘(th3r)、眼(yj3m)、便(bm4r)、步(bu4v)、知(vi1u)、浮(fu2uv)、岁(sv4u)、月(yt4j)、催(cv1r)、老(lk3l)、风(fg1p)、笑(xc4z)、尘(if2t)、缘(yr2s) |

#### 实战中验证的四条核心规则

**一、每字的最短编码 = "打到它在该前缀下排第一就停"**

不是"这个字可以用几码打"，而是"打到第几码时它排第一，当场停手"。判断方法：逐级缩短前缀，看首选是否还是目标字。

| 验证  | 字         | 当前输入  | 少一位会怎样      | 结论                      |
| --- | --------- | ----- | ----------- | ----------------------- |
| ✅   | 怎         | `zf`  | `z`→在       | `zf` 两码就排第一，`zf3` 多打了调码 |
| ✅   | 草         | `ck3` | `ck`→糙      | `ck3` 三码才排第一，不能省        |
| ✅   | 水         | `uv3` | `uv`→谁      | `uv3` 三码才排第一，不能省        |
| ❌   | 怎（用户实际输入） | `zf3` | `zf` 已经首选=怎 | 多打了一个 3，属于冗余            |

**二、词语匹配优先于逐字拆分**

`query_phrase` 通过完全匹配走词库索引，优先于 `split_sequence` 的机械切割。即使同一段编码按 C2 拆出来是错的，只要词库命中就直接上词。

- 祈 = qi2s（独立全码）、祷 = dk3y（独立全码）
- 词库存 `祈祷 qidk3`，取两字声母 q+d + 韵母首字母 i+k + 调码 3
- `qidk3` 按 C2 拆 → qi + dk3 → 七 + 导（错）
- 但 `query_phrase("qidk3")` → 祈祷（对），短语索引优先级高于拆分器
- **5 字母出 2 汉字 vs 8 字母逐字打 —— 词语简打是真正的效率核弹**

**三、四码全码字末尾必须加空格**

六句 12 个空格全部出现在四码全码字之后。原因：四码全码字的末字母恰好等于下字声母时，拆分器无法识别边界。

| 粘连案例  | 正确             | 无空格            | 结果                  |
| ----- | -------------- | -------------- | ------------------- |
| 倘 + 若 | `th3r` + `row` | `th3rr` + `ow` | ✗ th3rr 无效码         |
| 眼 + 中 | `yj3m` + `vs`  | `yj3mv`        | ✗ yj3mv 无效码         |
| 知 + 那 | `vi1u` + `na`  | `vi1un`        | ✗ vi1un 无效码         |
| 催 + 人 | `cv1r` + `r`   | `cv1rr`        | ✗ cv1rr 无效码（r 恰等于人） |
| 月 + 花 | `yt4j` + `hw`  | `yt4jh`        | ✗ yt4jh 无效码         |
| 缘 + 了 | `yr2s` + `l`   | `yr2sl`        | ✗ yr2sl 无效码         |

本质：C2 只能"往前看"（数字前 2 位切），不能"往后看"（不知道当前字是否已打完）。四码全码字的末码被 C2 当作下字声母的一部分吞入，一字错则全链崩。

**四、段内字可连续编码的条件**

同一段内，拆分器靠 C1/C2 自动切分，无需人工空格：

| 段内连续                                       | 拆分                              | 各条件                                       |
| ------------------------------------------ | ------------------------------- | ----------------------------------------- |
| `row` → 若 + 我                              | ro + w                          | C1（无数字 + len=3>2 → 每两位切：结果 3 位，先切 ro 剩 w） |
| `xnvsd` → 心 + 中 + 的                        | xn + vs + d                     | C1（每两位切）                                  |
| `vsdbkj4dk4` → 中 + 都 + 看 + 到               | vs + db + kj4 + dk4             | C1 切 vs,db → 剩 kj4dk4 → C2（数字 4→dk4）      |
| `nafu2uvugyipmck3` → 那 + 浮 + 生 + 一 + 片 + 草 | na + fu2uv + ug + yi + pm + ck3 | C2（各数字锚定）+ C1（无数字段两两切）                    |

段内可连续的前提：每个字的编码恰好落在拆分条件的"安全区"内。一旦有字需要四码全码且被 C2 盲视，就必须空格。

#### 简打三原则

从六句实战提炼出的可操作原则：

1. **每字打码当场停** — 打到它在该前缀下排第一为止。二码就够的不打三码（怎→zf 而非 zf3），三码才出的不打四码（草→ck3 而非 ck3c）。
2. **有词先查词** — 输入前快速判断：这几个字在词库里有没有注册？有就优先用词库编码（祈祷→qidk3），比逐字打好几个四码全码快得多。
3. **全码必空格** — 打完一个四/五码全码字，下一字开始前先敲空格。这不是"稳妥起见"，是 C2 的盲区决定了不空格必然出错。

### 简打设计的取舍：最短 vs 最流畅

简打生成器（`generate_jd_codes.py`）当前追求**每段编码最短**——逐字缩短到前缀唯一性的极限，再通过 `assign_spaces` 用最少的空格保证粘连安全。这是命名「简打」的应有之义。

但存在另一条路径：**适度增加编码长度，换取更少的空格/确认动作和更连续的打字节奏**。例如：

| 策略   | 编码          | 码长  | 空格+确认    | 体验          |
| ---- | ----------- | --- | -------- | ----------- |
| 简打最短 | `w m`       | 2   | 2次（每字确认） | 写写停停，需观察候选窗 |
| 中间态  | `wom`       | 3   | 1次（段尾空格） | 码长+1但节奏连续   |
| 全码流畅 | `wo3g mf0r` | 8   | 0次（2次自交） | 连续击键，自动上屏   |

三条路对应三种使用场景：

1. **简打最短** → 学习者。形码尚未形成肌肉记忆，空格确认比多记三个形码更友好。确认错一个字马上知道，不会打一串才发现首字就不对。
2. **中间态** → 熟练中的用户。形码已记住，但还在积累"哪一段可以少打"的判断力。多敲一两码省掉空格停顿，节奏更顺畅。
3. **全码流畅** → 形码已刻入肌肉记忆。不需要思考 `w` 还是 `wo3g`，手自己敲 `wo3g`，四码打完自动上屏，零停顿。

**这三条路径不是互斥的——它们是同一套编码体系在不同熟练度下的自然表现。** 所有人从 1 开始，随着熟练度提升自然滑向 2 和 3。

尽管简打需要大量边界确认问题（向后分隔的六种场景、向前分隔的三种情况、辅以空格和单引号），但从结果上看，它实现了最短平均码长——副歌六句 48 字全码 193 字符 → 简打 137 字符，省 29%。这体现了**前端五大机制配合的最优效果**：排序让短码优先、前缀匹配让未打全也能命中、自动拆分让连续编码自动分字、自动上字让常用字免空格直达、优先上词让词语一键上屏——五者协同，才使「最短码长且不打错」成为可能。因此简打机制仍然值得深入研究学习。
