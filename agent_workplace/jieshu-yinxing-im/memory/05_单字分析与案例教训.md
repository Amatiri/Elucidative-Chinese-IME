## 五、单字分析与案例教训

### 编码前查相关字：借力而非自律

**查表的本质不是"防止犯错"的纪律，而是借力——借已有编码的模式来减少底层思考量，同时一步解决重码问题。**

码表是逐步构建的。第一批字无码可查，只能从头推导，需要谨慎判断。而现在码表已经逐渐丰富，查表是适配现有模式和减少纠结的更好手段。因此对AI来说，查表尤其重要。

相关字分为两层：

#### 第一层：必须查（直接影响副码存废与路径选择）

1. **余字本身的编码**：余字在码表中的实际主码是什么、是否独体、可拆性如何。查一下就省掉"这个字怎么拆"的底层判断，顺带给出部首归属和可拆性，不用纯靠规则一步步分叉。
   
   - 反例：认为「斛的部首是角→k」——斛在码表 `hu2d`，部首斗→d，不是角。
   - 反例：认为「亥主码 d（亠）」——亥 `hl49`，独体复形，亠来自结构性可拆而非主码。

2. **前四码相同的全部字**：查同 ABCD 组有哪些字、各自的副码是什么、常用度排序如何。推导是在解决"怎么区分"的问题，查表直接告诉你"有哪些需要被区分"——在知道竞争者的前提下一步走到最优路径。
   
   - 反例：推导槲的副码时不知道 d 已被核占用，直接走捷径拿 d。

#### 第二层：建议查（辅助判断，避免意外撞车）

3. **同声旁字的编码**：同一声旁的其他字副码怎么取的，模式是否可借鉴。
   
   - 如糊的同声旁字还有煳 `hu2h`（火部，副码空）——煳的余字也是胡，但主码不同，不参与副码竞争，但可验证"胡"的编码一致性。

4. **多音字的全部读音编码**：当前字是否多音、其他读音下是否已有编码、互相是否有影响。
   
   - 如骠有两个读音，其中 pc4m 没有副码、bc1mp 有副码——不查就不确定其音区的编码状况。

5. **其他字中同一余字的副码选用**：同一个余字在不同字里的副码路径是否一致。
   
   - 如「累」在摞 `lo4us` 和漯 `lo4ut` 中的副码因常用度不同而分叉——查了才能理解为什么同为累却一个 s 一个 t。

#### 查相关字的命令模板

```powershell
# 查余字编码
(Get-Content "D:\USB\Py\输入法\dictionary.txt" -Encoding UTF8) | Where-Object { $_ -match "^斛" }

# 查前四码相同的全部字
(Get-Content "D:\USB\Py\输入法\dictionary.txt" -Encoding UTF8) | Where-Object { $_ -match " hu2m" }

# 查同音区全部字
(Get-Content "D:\USB\Py\输入法\dictionary.txt" -Encoding UTF8) | Where-Object { $_ -match " hu2" }
```

#### 操作流程

**查→推→验**，三步：

- 查：拿到全部相关字的实际编码
- 推：基于查到的编码做规则推导，不是基于想象
- 验：推导结果与相关字对照，确认无冲突

跳过「查」就直接推导，结论可能碰巧对（如槲的 k），但路径可能建立在虚构的前提上——意味着下次遇到类似情况还会按虚构逻辑走。

#### 查相关字后仍需规则推导，不可望码生义

**教训来源**：分析倝系字（乾、幹、擀、倝）编码时，多次根据码表结果逆向编解释，而非让规则在查到的编码框架下独立走通。

**典型错误**：

1. **望码生义——把编码结果当推导前提。** 看到擀 gj3us 有 s，就硬套「干→十→s（非部首字代替）」。但规则里余部首传递没有非部首字代替——干不在部首表，余部首传递本该取初码 g。s 的实际路径是一般余集合选取：倝→左上十→s。错在拿编码结果反推路径，而非用规则正向推导。

2. **忽略补码的源流关系。** 乾 gj15. 和幹 gj45. 的 `.` 是「干」的繁体/异体标记，从简体正字衍生而来。错在把 `.` 当成独立的独体判定结果，跳到表外部首代替去套。补码 `.F` 位的语义是繁异标记，不是主码层决策。

3. **部件来源不走解书拆分。** 倝 gj4sr 的 r，先编了「字源注释（康熙人部）」，后见拆分为「十、日、十、人」才纠正——日→部首表 r。如果不先走解书拆分，永远在猜。

**核心教训**：查相关字的意义是理解编码规律，不是拿到结果后逆向编解释。查到编码后仍需按规则正向走一遍，每一步都要有规则依据。编码结果是验证的对象，不是推导的起点。先走路再查表，不要先看表再找路。

### 编码实例:晰——副码"按规则推导 vs 码表实际"的冲突与理据揭秘

**编码**：晰 xi1rj

**理据原文（dictionary-data.js）**：

> `"晰":"日斤(四码→昔，副码m→膝)"`

**字形分析**（按汉典）：

- 结构：r. 日 析
- 形声：从日、析声
- 现代字形：**日｜木｜斤**（"析"在码表里可视为整体，但实际由"木"+"斤"组成）

**按规则推导**：

1. 主码：部首"日"在部首表 r 行 → **r**
2. 副码（走"余字解析码"路径，因为"析"不是部首表中的独立部首）：
   - 余字"析"成字（xi1m）
   - 余字初码 x = 整字初码 x → **音似**
   - 音似 → 优先取余部
   - 余字"析"是合体字（"木"+"斤"）→ 余部首传递取**首选余部**"木" → **m**（"木"在 m 行）；若首选被占则降级到"斤"（j 行）

**码表实际**：副码是 **j**，不是 m。

**冲突的真相**——xi1r 同组有 9 个字（按字母序排列）：

| 字     | 副码    | 来源分析                                                     |
| ----- | ----- | -------------------------------------------------------- |
| 昔     | 空     | 最常用字                                                     |
| 肸     | b     | 余字"𰅭" 难读 → 余部首传递 → "八" → b（理据："肉八... 𰅭 难读"）            |
| 曦     | h     | 余字"羲"=羊+我+兮（汉典字形），羲部首为"羊"（h 行）→ h（理据：日羊）                 |
| **晰** | **j** | **余字"析"=木+斤 → 余部首传递首选"木"→ m 被"膝"占用 → 降级到次余部"斤"（j 行）→ j** |
| 僖     | k     | 亻 + 喜（喜=士+口+丷 → 余部首传递取"口"）→ k（理据：人口）                     |
| 膝     | m     | 余字"桼"难读 → 余部首传递 → "木" → m（理据："肉木...桼 难读"）                |
| 晞     | p     | 日 + 希；首选余部"巾"=j → 被"晰"占用 → 递归下探到次余部"㐅"=p → p（理据：日㐅）      |
| 腊     | r     | 拆字=肉+昔，余字"昔"拆出"日"+龷，取余部"日" → r（理据：xi1：肉日）                |
| 傒     | v     | 亻 + 爪（理据：人爪） → v                                         |

**关键认知**："顺延至下一个可用字母"（rules.md §副码省略原则原文）不可字面判断为字母序顺延。它指**记忆 02 副码优先级链上的递归回落**：

- 余部首传递未占用 → 取首选余部部首码
- 首选被占 → 递归下探到余字的次余部（按字形可见顺序，如析=木+斤，希=巾+㐅）
- 次余部仍被占 → 继续递归（罕见）
  字母序是表象，**余部在余字字形中的可见顺序 + 优先级链** 才是本质。记忆 02 的"回落""递归"术语即指此。

副码序列 b/h/j/k/m/p/r/v——**按余部首传递的优先级链递归回落**（记忆 02「常用度决定谁优先拿余字主码，次常用字递归下探余字的余部」）：

- 肸/曦/僖/膝/腊/傒：首选余部未被占，直接取
- 晰：首选余部"木"=m 被占 → 递归下探到次余部"斤"=j
- 晞：首选余部"巾"=j 被占 → 递归下探到次余部"㐅"=p
- 不是字母序顺延——是"余部首传递优先级链上的递归回落"。

区分两条副码来源路径（rules.md §1.3）：

- **部首别码**（rules.md §1.3.1）：**余集合本身**就是部首表中的**独立部首**，且部首码 ≠ 初码。如余集合是"刂"（r 行别码部首），部首码 r ≠ 初码 d → 取部首码 r 当副码。
- **余部首传递**（rules.md §1.3.2 余字解析码下的子路径）：余字**不是部首表成员**，但成字 → 拆余字 → 取余字拆出的第一个部件的部首码。如腊 = 肉+昔，余字"昔"拆出"日"+"龷" → 取余部"日" → r。

**全部 8 个含副码字都走"余部首传递"**——没有一个走"部首别码"路径。这说明 xi1r 组里所有"非最常用字"的余字都**不是**部首表中的独立部首。

**理据字段的解读关键**（参考 06_其他约定性方法论.md §理据添加方法）：

- **"日斤"**：不是"拆到余字内部部件"。这是**含副码合体字的理据格式**——第一个字是部首（日），第二个字是副码字母实际指向的部件（斤）。理据里不写"+"，直接两字并排。如同"汐=水夕"（氵+夕→部首水+副码部件夕）、"沂=水斤"（氵+斤→部首水+副码部件斤）。所以"晰"的副码 j = 部件"斤"，不是"析"。
- **"四码→昔"**：前四码 xi1r 与"昔"冲突 → 需要副码（标明同组空副码字是谁）
- **"副码 m→膝"**：**作者知道规则首选 m，但同组"膝"已占用**，副码顺延到下一个可用字母 = j

**教训**：

1. **理据是编码层的"元数据"**——读懂它比看主码表更能理解副码来源。`"晰":"日斤(四码→昔，副码m→膝)"` 完整交代了字形拆分、同组冲突、副码去向。
2. **同组副码冲突不是个案**——同声旁多字（如 xi1r 组 8 个）必然出现副码争夺。规则首选在占用后失效，最终副码由**字母序均分**决定。
3. **部首别码 ≠ 余部首传递**——这次最初推导误用了"部首别码"路径（"析的部首木 → 部首别码 m"）。错。"析"不在部首表（m 行只列"木、彡、釆、马、门、皿、毛、目、矛、米、麦"），"部首别码"条件（余集合本身是部首表中的独立部首）不成立。正确路径是"余字解析码"下的"余部首传递"：余字成字 → 拆出"木"+"斤" → 取余字部首"木" → m。两条路径结果都是 m，但适用条件不同，不能混用。
4. **余字难读时不能取余音**——肸 xi1rb 的余字"𰅭" 是扩展 B 区罕用字，难读 → 走余部首传递而非余音。理据"肉八... 𰅭 难读"明确说明这个分支。这与"膝"的"桼 难读"是同一个机制：**余字难读直接降级到余部**，不走余音路径。
5. **副码推导与修正的精确分层**——"查同组"不在推导链内，而在"推导后修正"阶段：
   - **推导链**（无需求证占用）：拆字 → 主码 → 余部首传递 → 首选余部 → 部首码 → **副码优先 = R(c)**（推导完成，与码表无关）
   - **修正链**（可选，借力）：查同组竞争者 → 若 R(c) 被占 → 沿优先级链递归到次余部 → 副码 = R'(c)
   - 若不查同组：直接给 R(c)，遇用户反馈冲突时回头重推到 R'(c)。这是"减少曲折"，不是"推导步骤"
   - 晰：R(晰) = m（推导完成）→ 查同组发现膝占 m → 递归 → j
   - 晞：R(晞) = j（推导完成）→ 查同组发现晰占 j → 递归 → p
   - **关键区分**：副码"优先"与"结果"是独立的两件事。优先（m / j）由规则决定，结果（j / p）由占用关系决定。

### 编码实例:瘆、珩

| 字   | 拼音   | 音码  | 主码  | 副码  | 完整编码  | 分析要点                                  |
| --- | ---- | --- | --- | --- | ----- | ------------------------------------- |
| 瘆   | shèn | uf4 | b   | s   | uf4bs | 疒+参,余字"参"与整字音似,取余部"厶"(部首码s)           |
| 珩   | héng | hg2 | w   | 无   | hg2w  | 王+行,余字"行"音似(háng初码h=整字h),但hg2w无重码故无副码 |

**瘆的详细分析:**

- 瘆 = 疒(左)+ 参(右),为合体字
- 音码:shēn → u(sh)+ f(en)+ 4(去声)= uf4
- 主码:疒部 → b
- 余字"参"(shen1)与整字"瘆"(shèn)**音似**
- 音似时取余部:参 → 部首"厶"(si1),部首码 = **s**
- 完整编码:**uf4bs**

**珩的详细分析:**

- 珩(héng)= 王 + 行
- 前四码:hg2w
- 余字"行"(xíng/háng),háng初码h = 整字初码h → 音似
- 音似取余部:行 = 彳 + 亍,取"彳" → 部首码 t(副码候选)
- **但** hg2w 已无重码 → 无需副码
- 最终编码:**hg2w**

**教训**:副码只在**前四码冲突**时才需要,不能因为"能算出来"就加副码。

### 羲取戈不取禾的三重统一

**副码来源**:编码 xi1hg,主码 h = 羊,副码 g = 戈。

**三条独立路径均指向戈**:

**路径一 - 直觉(视觉权重)**:戈在余集合中结构庞大、笔画突出,是绝对的视觉重心;禾偏居左上、又小又挤。直觉强烈指向更大更显眼的戈。

**路径二 - 规则(余部首传递)**:余集合中含一个以戈为部首的隐含合体字 → 余部首传递取戈的部首码 g。这是主线规则,不需要走到「取首个音异部件」的备用规则。禾那条路反而是备用规则。

**路径三 - 字源(讹变跳过)**:羲 = 兮(声旁)+ 義(形旁)。禾在字源上根本不是禾,而是兮的隶变讹变--不表音、不表义,按规则「隶变后变得模糊难以辨认的部件,一般跳过不取」应被跳过。義的核心表义部件是我,我的部首是戈。取戈 = 以义定形。

**核心洞见**:三重路径殊途同归 → 戈不仅仅是「两个合法选项中选出来的」,而是正解。禾来自讹变部件,规则上就该跳过。好的规则本身就是对最优解的归纳,不是发明出来的约束。

**教训**:分析疑难字编码时,不能只走一条路径。直觉、规则、字源三条路各自独立验证,如果全部指向同一个结论,就是最优解;如果出现分歧,才需要优化分配的权衡。

### 嗤的编码与声旁演变

**嗤 ii1kl 编码分析**:嗤 = 口(k)+ 蚩。蚩 = 虫(l,形旁)+ 之(㞢,声旁)。副码取 i(之余音)。

**副码 i 的来源**:之(㞢)初码 v(zhī)。章母(之)和昌母(蚩)在中古音中同属照组,但现代已分化——之不再被识别为蚩的声旁,故走音异取余音路径,取余音 i(chī 余音初码)。这是音变造成的编码结果,并非编码错误。

**编码作为汉字分析材料**:嗤的编码过程自然揭露了声旁关系的现代可辨性。之作为蚩的声旁在章昌分化后已不可辨——这个信息不需额外学习,从编码推导中自然浮现。

### 合体字部件识别必须逐笔确认,不可凭轮廓感

**教训来源**:分析「鸱」ii1nd 时,将左部件「氐」(dī)误认为「氏」(shì),导致余音推导从 d 错为 u。

**错误根因**:「氐」和「氏」差下面一个点,轮廓相似但初码不同(d vs u)。凭一眼轮廓判断部件,没逐笔确认。

**规则**:合体字拆分后,余字必须逐笔确认--尤其是形近部件:

| 容易混淆        | 区分点    |
| ----------- | ------ |
| 氐 vs 氏      | 氐下有点   |
| 未 vs 末      | 上横短长   |
| 己 vs 已 vs 巳 | 封口程度   |
| 日 vs 曰      | 高矮宽窄   |
| 人 vs 入      | 捺的起笔位置 |
| 干 vs 千      | 首笔横/撇  |
| 土 vs 士      | 横的长短   |

**教训**:每次拆分后,确认余字身份时读出余字读音--如果读错了,初码就错了。

### 余字初码与部件初码不可混淆

**教训来源**:分析「锯」副码时,将余字「居」的初码 j 错误地安到「尸」头上,说"尸的部首码 s ≠ 初码 j"。实际上尸的拼音是 shī,初码 u。

**错误根因**:余部拆开后,子部件的初码要根据子部件本身读音重新计算,不能沿用余字的初码。

**正确流程**:

- 锯 = 钅(主码 j)+ 居
- 居初码 j = 整字初码 j → 音似 → 取余部
- 居 = 尸 + 古 → 尸在部首表中,部首码 s,尸初码 u ≠ s → 部首别码 s
- 锯"可选"副码 = s
- 但是"锯"是前四码中最常用的字,实际上无需副码,即空副码。

**关键区分**:

| 部件  | 读音  | 初码  | 在部首表? | 部首码 |
| --- | --- | --- | ----- | --- |
| 居   | jū  | j   | 否     | 无   |
| 尸   | shī | u   | 是     | s   |

「居」的初码 j ≠「尸」的初码 u。递归进入子部件后,音似判断也重新以子部件初码为基准--尸初码 u ≠ s → 有别码;若音异路径取余音,余音也取子部件初码而非余字初码。

**教训**:每次递归进入更细粒度部件时,必须重新计算该部件的初码,不能携带上一层的初码。 

### 功能7查询字码：制作编码对照表的便捷性

`main.py` 的功能 7（查询字码）支持连续汉字输入，一次回车即可输出整段文字的全部编码，同时标注未录入字。

**操作流程**：

1. 运行 `python main.py` → 选择 7
2. 粘贴或输入任意长度的连续汉字
3. 回车，系统按空格分隔输出每个字的编码
4. 多音字自动列出全部候选编码
5. 底行标注「未录入汉字：X Y Z」

**便捷性体现**：

- **一句话上码**：整首诗、整句话粘贴进去，一次性拿回全编码，无需逐字查询
- **多音字暴露**：一个字的多个读音和编码并列显示，天然形成对比学习材料
- **码表边界显影**：未录字直接点名，缺口一望而知
- **制作对照表零成本**：适合教学场景——举《静夜思》《关雎》为例，全诗编码一次性输出后逐字讲解

**作为教学工具的设计意图**：批量查询不是为了效率而是为了全景视野。教师拿到一首诗的全部编码后，能在同一屏上对比同部首字的编码一致性（如寤寐同取宀 b）、观察音区分流效果（荇 x;4c vs 菜 cl4c 声母不同天然分流）、发现五位字的分布规律（全诗仅一字需副码）。

### 音形码组合中的汉字音韵与意象美

解书编码不仅是对汉字结构的分析工具，编码结构本身有时与汉字的语义意象形成共振。

**「疑 yi2bu」——编码结构与语义的同构**：

疑 = 匕(b) + 矢(u)。一把匕首，一支箭矢——这两个部件恰好构成了「疑」的语义场：持匕者何意？引矢者何向？不确定，不可解，正是「疑」。

这是巧合，但巧合一旦被发现就不会被忘记。用户记住「疑」的编码不需要死记，只需要看到这个字时想到它由匕和矢组成——这恰好就是主码和副码的来源。编码不是在给字贴标签，而是在拆开字给你看它里面有什么。

**五位字的节奏意义**：

《静夜思》全诗 20 字中 19 字均为四位，仅「疑」一字为五位。像诗句中多停留一拍——编码结构与诗意的呼吸节奏完全同构。码长不只是输入效率指标，有时也是诗学节拍的天然记谱。

**设计启示**：好的编码体系应该让编码推导过程本身就是汉字赏析过程。编码越能暴露汉字部件的语义关系，记忆负担越轻——因为用户不是在背编码，而是在理解字。

### 「月」等超级常用字在码表中的滞留性

**「月 yt4j」不是规则的例外，而是规则进化过程中留下的化石。**

**现状**：月在独体字分类出现前就已定型编码。当独体/合体判定规则引入后，月的旧编码因以下三个原因保留不动：

1. **过于常用**：月是绝对高频字（日月年月），改动其编码等于让所有已掌握的用户重新适应
2. **规则是解释性的**：规则服务于码表而非支配码表。码表中已稳定运行的编码，不需因规则细化而强行修正
3. **人的判断是终极裁决者**：开发者审阅后决定保留原编码

**「滞留性」的含义**：超级常用字在码表中有「惯性」——它们的编码一旦稳定，后续规则细化不会推倒重来。这不是设计缺陷，而是「规则为码表服务」这一架构原则的必然体现。

**此模式在码表中的反思推广**：

| 字   | 规则预期       | 码表实际         | 滞留原因 |
| --- | ---------- | ------------ | ---- |
| 月   | yt49(复形⁹)  | yt4j(拆冂)     | 超级常用 |
| 进   | jn4zq(余音j) | jn4zw(引用繁体隹) | 优化分配 |

规则文档中说「规则是解释性的，码表才是第一性」——月在码表中的滞留正是这一原则最直观的例证。

**对学习者的提示**：遇到「月」这类字时，不要纠结「为什么规则和编码不一致」，把它当特例记住即可。规则体系内保留少数特例不会破坏编码的可推导性——因为特例本身就是学习过程中最容易被记住的点。

### 以「逑」串起的副码规则全链路

「逑」的编码推导过程串联了副码体系的多个核心规则，是理解「音似/音异分流」的最佳教学案例。

**完整推导链路**：

```
逑 = 辶 + 求
├─ qq2    音码（qiú 阳平）
├─ z      主码（辶 ∈ 部首表）
├─ qq2z   前四码 → 与「遒」冲突！
└─ 进入副码推导 →
      ├─ 余字「求」→ 初码 q = 整字初码 q → 音似
      ├─ 音似 → 优先取余部
      ├─ 求是独体（qq26，大形⁶）→ 触发独体字可拆性判断
      │   ├─ 通道一（分离性）：不满足（水形已成有机整体）
      │   ├─ 通道二（字源性）：不满足（拆不出独立的「水」）
      │   └─ 通道三（结构性）：不满足（无丷亠冖勹口）
      ├─ 三条通道全不通 → 求不可拆 → 余部不可取
      └─ 回落余音 → 副码 q
```

**这条链路串联的规则节点**：

1. **副码存在性前提**：前四码 qq2z 冲突（遒已占用）→ 才需要副码
2. **音似判断**：整字初码 q = 余字初码 q → 音似 → 优先取余部
3. **独体字余字三通道可拆性验证**：分离性/字源性/结构性，任一满足即可拆；全不满足则不可拆
4. **余单笔画规则的正确适用范围**：「余集合仅剩单笔画」才触发——整个余集合成字（求）时，不适用单笔画规则
5. **音似/音异分流的回落机制**：音似优先取余部，但余部不可取时回落余音。规则说「优先」而非「只能」，两边是镜像的
6. **副码 q 的结构信号**：q = 整字初码 = 余字初码，携带「音似但不可拆的独体余字」结构信息
7. **常用度天然由码长区分**：遒（更常用）→ 空副码四位；逑（次常用）→ 带副码五位

**音似/音异分流不是两棵独立的树**：

```
传统误解：              实际设计：
  ┌─ 音似 → 余部         判断音似性
  变更                     ├─ 音似 → 余部能取吗？
  └─ 音异 → 余音                      ├─ 能 → 余部
                                     └─ 不能 → 余音（回落）
                               └─ 音异 → 余音能取吗？
                                         ├─ 能 → 余音
                                         └─ 不能 → 余部（回落）
```

两边是镜像的。拒绝了一条路不等于承认失败，而是把另一条路从「废弃」升级为「唯一可用」。

**逑 vs 进——同一结构、不同副码路径的对照**：

| 维度   | 进 jn4zw       | 逑 qq2zq  |
| ---- | ------------- | -------- |
| 余字   | 井             | 求        |
| 余字性质 | 独体，不可拆        | 独体，不可拆   |
| 音似性  | j=j（音似）       | q=q（音似）  |
| 余音   | j             | q        |
| 实际副码 | w             | q        |
| 路径差异 | 引用繁体「隹」别码 → w | 回落余音 → q |

「进」如果按规则推导本该取余音 j（与逑完全对称的路径），但因为 j 区分度不够，走了优化分配的繁体引用路径。这说明在「音似且独体不可拆」的困境中，回落余音是默认路径，优化分配是升级路径——两条路径都是合法的，选择取决于区分度。

**教学价值**：一个逑字串起了副码体系的几乎全部关键概念，可作为教学材料中的「副码速通案例」。

### 龹的余部取码序列：不是特例，是余集合选取的正常运作

**场景**：「豢 hr4um」副码 m 的来源分析。

**初步理解（错误）**：把「丷→d → 占 → 釆→m」理解为古今字形切换的特殊机制。

**正确理解**：这就是**一般余集合选取规则**在正常运作——龹有两个可识别的余部：

```
d → m
│   │
│   └─ 龹的另一个余部「釆」→ m
└─── 解书拆分取最上端 →「丷」→ d
```

不需要引入「换字形视角」的概念。龹本身就能拆出两个余部（丷和釆），按一般余集合选取的优先级序列接力——首选 d 被涣占 → 进入下一个余部 → m。

**核心洞见**：这不是特例化机制，而是余集合选取规则在一个有两个可识别余部的部件上的自然表现。序列里有几个余部，就依次尝试几个，仅此而已。并入既有逻辑比单独列一条规则更干净。

### 捷与疌：余字整体归部

**编码**：捷 jx2uz，副码 z = 走部。

**同组**：洁 jx2u（空）→ 拮 jx2uk（k）→ 捷 jx2uz（z）。

**分析**：余字「疌」不走一般余集合选取逐个拆部件，而是**整体归部**——疌整体字形像「走」的变体，字义上「捷」与速度/快捷相关（走捷径），形义合力指向走部(z)。

**与龹的对比**：

|     | 龹（豢的余字）        | 疌（捷的余字）                  |
| --- | -------------- | ------------------------ |
| 首选  | 解书拆分取上端 → 丷(d) | 整体归部 → 走(z)              |
| 次选  | 整体归部 → 釆(m)    | 一般余集合选取（被占/区分度不够，比如“又”k） |
| 依据  | 字源字形           | 字形联想 + 字义关联              |

两条路径结构不同：一般拆分走不通或被占 与 余字整体归部 没有明确先后，靠现代字形和字义综合判断取码。

**分层理解**：打字层只需知道 z 是首选副码；理解层才追究疌整体归走部的形义逻辑。不需要把疌拆成又、止再去分辨。

### 麾：部首优化分配从麻到毛

**原编码**：hv1gm（康熙归麻部 → 麻简并广 → 主码 g；与辉 hv1g 同四码 → 需副码 → 余字毛音异 → 取余音 m）

**新编码**：hv1m（部首重新认定为毛 → 主码 m）

**优化依据**：

1. 麻族字有稳定的取部模式：麻不是形旁时，取真正的形旁为部首——摩取手(u)、磨取石(s)、魔取鬼(v)。麾的麻同样是声旁（靡→麾），毛才是表意部件（麾指旌旗，毛为旄尾/旗饰）。把部首从麻改为毛，只是补齐摩/磨/魔已有的模式，不是制造例外。
2. hv1m 码区为空，无冲突。
3. 4 码（hv1m）比原 5 码（hv1gm）短，缩短了输入路径。
4. 康熙字典归麻部是形体归部（麻在上很显眼），但在解书音形的优化分配框架下，「取真正的形旁」优先。这不是推翻康熙部首，而是延续同族字的一致性。

**教训**：部首优化分配时，同族字（同一声旁的多字）的取部一致性是重要判断依据。麻声旁家族在码表中有清晰的「取真正形旁」模式，麾不应例外。优化分配不是孤立地判断单个字，而是在族内寻找一致性。

### 回答流程类错误：三次「先有结论再找依据」

**场景**：用户问「如果没有词语编码，打 ytdu 时会出现什么情况」，后续追问自动拆分机制。

**错误1 - 未读源码即断言拆分机制**：第一轮回答时说「前端预先根据字典算出可能的拆分点」——这与 `split_sequence` 的实际逻辑完全相反。实际是先机械切割（每两字符一刀/遇声调切/五码打全切等），切完再逐段去字典前缀匹配。正确的做法是：读 `dictionary_frontend.py` 的 `split_sequence` 函数，确认切割条件后再回答。

**错误2 - 未查字典即判断候选排序**：断言「yt 第一候选是阅」「du 第一候选是读」时，一个前缀都没查。字典就按编码字母数字排序，yt1（曰一声）天然排在 yt4（阅四声）前面，du1 排在 du2 前面。用常识（「常用字排前面」）去猜编码排序是根本性错误——编码排序按字符串比较，跟常用度无关。

**错误3 - 条件1判定读半截**：说 `ytd` 长度=3 不满足条件1。源码是 `len(part) > 2`，3 > 2 成立，条件1会触发。错误原因是脑子里把「三码不够」和「不切」画等号，然后倒推条件不成立。正确的做法是逐行模拟 `split_sequence("ytd")`，得出 `yt'd` 的结果，再指出问题在于 `d` 段前缀太短而非「不会切」。

**三个错误的共同模式**：先有结论再找依据，而不是先查证据再下结论。

**正确流程固化**：讨论编码或前端行为时，必须执行 查源码 → 查字典 → 推演 三步，不能跳过任何一步。

### 副码的双重面孔：编码层的区分信号 = 输入层的污染信号

同一个字母，在编码层是区分功臣，在输入层是冲突源。这不是系统的 bug，是信息复用的天然代价。

**两阶段的视角切换**：

```
编码阶段（过去时）：          输入阶段（将来时）：
─────────────────          ─────────────────
余字推导 → 副码              副码字母 → 后接字初码 → 冲突域
"钎为什么有副码 s"            "钎的副码 s 会在哪里炸"
```

- **编码层**：副码存在的唯一目的是区分同四码的重码字。钎 qm1js 的 s 来自余字「千」→ 音似 → 余部首传递（康熙十部）→ s。s 在编码层是「帮系统把钎和铅分开」的信号。
- **输入层**：同一个 s，在后接字初码为 s 时（如丝 si1s、酸 sr1y），触发场景1（5）劫持——qm1jsi1s → 钎i1s（自动上字抢断）。s 在输入层变成了「帮系统把铅丝误判为钎+残码」的污染源。

**不是字母变了，是看字母的立场变了。**

#### 脑内构拟场景（5）：从「查到」到「看到」

掌握这条对应关系后，每个有副码的字都在脑中自带一张**隐式冲突图**。不需要真的输入到撞墙才发现——看到编码就能预判：

```
字        副码    冲突域（后接字初码命中即需空格）
──────   ────    ───────────────────────────
钎 qm1js  s       所有 s 初码的后接字（丝、酸、素、算…）
箓 lu4zu  u       所有 u 初码的后接字（上、水、手、山…）
逯 lu4zi  i       所有 i 初码的后接字（程、长、成、车…）
漯 lo4ut  t       所有 t 初码的后接字（土、天、田、头…）
```

这不是需要死记的清单——它是**可推导的**：知道一个字的副码来自哪里，就能倒推出冲突域。推导链在两个方向上完全可逆：

```
编码方向：千 → 十 → s      （副码为什么是这个字母）
冲突方向：s → 所有 s 初码字 → 构成冲突域  （这个字母会在哪里撞车）
```

两个方向共享同一条知识——学一次，两个方向同时通。这不是在认码，是在**认码和用码之间建立双向回路**。这是编码素养的准确含义。

#### 与「同四码同余字同需副码」的关系

同四码同余字同需副码那条记忆处理的是编码层内部竞争——同组内的字怎样分配副码（摞拿累主码 s，漯递归取田 t）。副码双重面孔这条记忆处理的是编码层与输入层的跨层碰撞——编码层已经定好的副码字母，在输入层如何触发劫持。

两者是副码规则的**内表面**和**外表面**：

- 内表面：副码在同组内的分配逻辑（编码层自身的自洽性）
- 外表面：副码字母对后续输入的影响（编码层对输入层的溢出效应）

理解副码不能只看它「怎么来的」，还要看它「会去哪里」。前者是编码推导的全部内容，后者是输入体验的全部预判——两者合一才是对副码的完整认知。

### 冷僻读音可主动放弃收录：圫 yù 的取舍

**核心原则**：

> **多音字可适当忽略罕见读音；单音字无论多生僻都必须录入。**

**为什么单音字必须录**：单音字没有其他读音可分担——如果一个字只有一个音，那么"想打这个字"的唯一路径就是该音。无论这个音多么冷僻，拒绝录入等同于**完全屏蔽这个字的输入路径**，这超出了"优化"的范畴，属于**输入能力的缺失**。而多音字则不同——用户想打圫时，可以走 to1t（tuō）或 vp1t（zhūn），**有替代路径可达该字**，放弃 yù 不影响"圫"的可达性。

**案例**：「圫」字在《康熙字典》《汉典》有三读 tuō / yù / zhūn。解书码表已收录 **to1t**（tuō）和 **vp1t**（zhūn），未收录 yù 读音——这是**主动决策**而非遗漏。

**为什么不收录 yù**（多音字层面）：

1. **yù 在圫字自身里几乎不出现**：圫的 yù 读音仅作为「墺」的古字存在（《康熙字典》：「墺，古作圫」），它不携带独立的字义——脱离「墺」单读 yù 时语义基本为零。
2. **同音区已被充分占用**：yu4 音区已有 36 字余，前四码 yu4t 已被「域 yu4t」占用，要给圫加 yù 编码得抢占 yu4t 副码区槽位，**挤占成本远大于收益**。
3. **用户已有可替代路径**：想打"墺"读音时用 `ok4t`（坳）或 `ok4td`（墺）。最关键：**想打"圫"这个字本身时，to1t 已经能命中——放弃 yù 不影响圫的可达性**。

**决策原则——「冷僻读音可放弃」的判定条件**（同时满足才考虑放弃）：

1. 该字是**多音字**（非单音字）——单音字不在放弃范围内（参见核心原则）
2. **该读音在字义上不独立**：仅作为异体字读音/通假字读音/古文借音存在 → 它依附于别的字，不属于本字
3. **已有其他编码可达到本字**：用户的"想打这个字"的诉求能被其他读音的编码满足
4. **已有更常用的同义字承担该音**：yù → 墺 ok4td；用户查正字ji即可
5. **新增成本过高**：要抢占新 ABCD 槽位 / 走补码后缀 / 制造重码冲突，三选一都有代价
6. **用户主动确认放弃**："圫只能通过 to1t 和 vp1t 打出，yù 过于生僻，解书音形不再收录"

**与"补码路线"的边界**：

`memory/02_副码与补码规则设计.md` 末尾「坖 ji4x.t」案例提供了**补码路线**作为冷僻异体字的兜底——但补码也有成本（多一个 `.t` 后缀、要查重、占后缀表空间）。

**两者权衡**：

| 决策                  | 适用场景                                   | 不适用场景                    |
| ------------------- | -------------------------------------- | ------------------------ |
| **补码路线**（如坖 ji4x.t） | **单音字** + 异体字极不常用（仅用于人名/古文僻用）+ 正体字在码表中 | 多音字（可走"放弃收录"）            |
| **放弃收录**（如圫 yù）     | **多音字** + 异体字仅作古字，无独立字义 + 用户主动确认放弃     | **单音字** / 异体字在某种语境里被频繁使用 |

**判断口诀**（两阶段判定）：

```
阶段一：这个字是单音字吗？
 ├─ 是 → 无论读音多冷僻，必须录入该音（无例外）
 │        → 录入方式可选：主码独立 / 补码继承（极不常用时走补码，如坖 ji4x.t）
 └─ 否（多音字）→ 进入阶段二

阶段二（仅限多音字）：这个读音脱离正体字之后，能独立支撑一句话吗？
 ├─ 能（异体字有独立语境使用）→ 补码收录
 └─ 不能（如圫 yù 仅作墺古字，无独立语义）→ 主动放弃
```

**对应码表状态**：`圫` 现有 `to1t`、`vp1t` 两个编码，**不再追加 yù 音编码**。如果用户后续真遇到"圫读 yù"的硬场景，临时用正体字「墺」或用其他读音编码代替即可。

### AI 立词批处理时的四类连锁错误

**场景**：用户让 Agent 一次为 8 个词（高兴/认识/熟悉/偏好/技能/记忆/路径/前端）推立词编码，前几轮内连续出错，最终由用户逐条纠正才到位。错误密度极高，几乎每轮都有新错。

**共同根因**：**没有走完「查→推→验」三步**，而是把规则名称当「可以凭印象推导」的令牌。该查的不查、该验的不验、用情绪性叙述（"看起来安全"）替代工具调用。

#### 错误 1：用「触发=0」就报"安全"，未追问根因（`gk1x;` 自交未察觉）

**事实**：Agent 首轮给「高兴」的编码是 `gk1x;`（5 码带调），只看了 `jd_analyze` 的「触发 0 次」输出，就放进"安全"清单。

**实际结果**：用户用 jd_analyze 的自动上字模拟验证，发现 `gk1x` 在第 4 码时 `gk1x` 前缀唯一对应「睾」，自动上字抢断，`;` 永远进不了缓冲区——**确实自交**。Agent 不仅推错，而且验证时漏检。

**教训**：

- `jd_analyze` 输出「触发 N 次」只表示**整段**累积匹配。**对于"长编码的中间某段子交"**，输出可能仍显示「触发 0」——脚本默认查输入整段，不是路径上每个前缀都查。
- 正确做法：验证长编码时，**自己**用脚本按 1/2/3/4... 逐码查每段前缀是否有唯一候选（自动上字条件：长度 > 3 且唯一），并用 `CLI_emulation` 实敲一遍确认。

#### 错误 2：声韵码凭印象拼写（`shú` 错拼为 `ub`）

**事实**：Agent 把「熟 shú xī」的熟声母韵母拼成 `ub`（sh→u, ou→b），给出 `ubxi1`。

**实际**：搜狗双拼中 shóu 才是 `ub`，shú 是 `uu`。shu 的 u 声母 + u 韵母都是 `u`，**两个 u**。

**教训**：

- 查 `dictionary.txt` 是一手答案：`Where-Object { $_ -match "^熟" }` 立刻看到 `ub2h` 和 `uu2h` 两个全码。
- **韵码字母表要固化在脑中**，常见歧义：u 是「sh/u」双义，b 是「ou」单义。

#### 错误 3：双拼字串拼接错位（`jiyi` 错成 `jyiy`）

**事实**：Agent 把 `ji` + `yi` 拼成 `jyiy`，多出一个 `y`。双拼是 `ji yi`，不是 `jy iy`。

**根因**：把字 1「记」的韵码 `i` "越界"塞进字 2 的头部，于是两个 2 字母双拼变成了错位的 4 字母串。

**教训**：

- 二字词双拼永远是 **`[字1双拼 2] + [字2双拼 2]`** 的直接拼接，**中间没有任何字符**。
- 容易出错的场景：当字 1 韵码 = 字 2 声母时，逐字母读起来像 4 个不同字母对，但绝不能拆错位。
- **核验方法**：把编码切回双字，逐字查 `dictionary.txt` 的整字码比对。如「记 `ji4u`」中 `ji` 是音码，立刻定位声母 j + 韵母 i。

#### 错误 4：档位判断凭情绪（3 码「最简码」当 4 码常用档用）

**事实**：Agent 把「偏好 `pmh`」「记忆 `jiy`」标为 3 码，列入候选。

**实际**：规则明确说 3 码「**基本不用**」——3 码是「极简基本码档」，理论预留位，**不**是日常档位。日常档是 4 码（第一字双拼 + 第二字双拼）。

**教训**：

- 档位不是"能取就用"，要看规则档位的语义：3 码 = 理论预留，4 码 = 常用，5 码 = 消歧。每加 1 码都有明确语义。
- 现有 3 码词条在 `ciyu.txt` 里基本只有"没有 已经"这种口语极高频，不是"短就好"。
- **一致性优先于最短**：当 8 个候选大部分是 4 码、少数 3 码时，先警觉"是不是都该 4 码？"而不是"留下少数的 3 码"。

#### 元教训：批处理时错误会传染

**观察**：本轮 8 个词的立词推导，前 5 轮连续出现 4 个独立错误（编码、内容、档位都错），错误密度远高于日常。

**反思**：连续推导多个相似任务时，Agent 进入「批处理模式」后倾向**复用前一个推导的结论，导致错误也在批处理间传染。

**对抗方法**：

- 每条推导必须重新**完整走一遍**查→推→验，**不复用前一条结论**
- 不要批量一次报结果给用户——分批（每 2-3 条一停让用户验收），把传染限制在最小粒度
- **见到自己前一条输出已错立刻停**，深查一次，而不是顺着错的继续推下一条

**本节整体教训一句话**：立词这种"低层重复工作"对 AI 最危险——因为看起来简单、可以用规则名加速推导，**但加速路径 = 偷工路径**。任何"凭印象就敢推"的瞬间都是错。**老老实实查表，是这种工作里唯一的安全动作。**

### 元教训：理据是事后解释，不是推导依据

**问题**：分析"晰"过程中，多轮依赖查 `dictionary-data.js` 的 rationale 对象才能解释副码走向。一旦理据字面是 "??"（码表生成时的字符编码问题），就完全卡住。

**根本错误**：把"理据"当成规则的替身。理据 = 事后写给初学者看的"为什么这么取码"，**记录的是取码结果，不是取码规则**。

**正常推导不需要理据**：

```
字形拆 → 取部首 → 查同组竞争 → 按规则推副码
```

清晰推导（不依赖理据）：

```
晰 = 日 + 析
├─ 主码：日 → r
├─ 前四码 xi1r → 同组竞争者 "昔 xi1r" 空副码 → 冲突
├─ 副码推导：余字"析"成字 → 初码 x = 整字 x → 音似
│   → 音似取余部 → "析" = 木 + 斤 → 取"木"部首码 m
├─ 同组已有 xi1rm（膝）→ m 被占 → 字母序顺延 → j
└─ 副码 = j，编码 = xi1rj
```

整条推导链完全在规则 + 同组查表内完成。理据（"日斤(四码→昔，副码m→膝)"）只是事后记录——有了它，初学者不用走推导链就能看懂；**没有它，推导照样成立**。

**为什么我之前做不到**：

1. **跳过"查同组"**——副码推导必须先查同组竞争者。没查就直接信"规则首选 m"，所以得出 j 看起来像规则外产物，必须借理据才能解释
2. **遇到冲突就外求**——不查理据就觉得"解释不了"，但查同组就能推出来。理据是"知道结果后的解释"，不是"推导的依据"
3. **把"理据"和"规则"地位颠倒**——理据是规则的投影，不是反过来。遇到推理困难去翻理据，等于把"理解"外包给一个外部数据源

**强信号**：码表里"肸""晞""桼"等字的理据字面是 "??"（码表生成时字符编码坏掉）。这种情况下去抠字面没意义——**回退到规则推导即可**。

**修订后的副码推导流程**：

1. 字形拆（视觉可拆 → 部首 + 余字）

2. 取主码（部首查部首表）

3. **查同组**（前四码相同的全部字 + 各自副码 + 常用度排序）——**这一步不能跳过**

4. 按规则推首选副码（部首别码 → 余字解析码 → 音似取余部 / 音异取余音）

5. 首选被占 → 沿副码优先级链递归回落（记忆 02 "常用度决定谁优先拿余字主码，次常用字递归下探余字的余部"），不是字母序顺延

6. **整条链完成才查理据**（仅用于"事后核对 + 写给初学者看"，不是推导的输入）

### 编码实例: 瞳/僮/曈 —— 童余部双双归 l，简并是副码层的第二深度回落

**背景**：童声字 瞳(ts2ml)/僮(ts2rl)/曈(ts2rd) 的副码推导，纠正两个错误认识。

**童的两个余部都归 l**：

- 余字童 = 立(上，部首) + 里(下)
- 立：表外 → 取初码 l
- 里：表内 l 行 → 部首码 l
- 两个余部殊途同归到 l，l 是童声字副码的"天然归宿"，也是最挤的码位

**错误认识一（常用度）**：曾说"如果觉得瞳比桐更常用，空副码归属可重新斟酌"。错。常用度由判定链唯一确定：三字都可读、含义丰富 → 比声旁匹配（桐=同 tóng、瞳=童 tóng 均满分，彤=丹 dān 不匹配出局）→ 桐瞳并列比笔画（桐10 < 瞳17）→ 桐最常用。规则已给出确定答案，不应开放化。

**错误认识二（简并的定位）**：曾说"简并立→亠是主码层路径，副码余部首传递层不走简并"。不完整。正确：**副码层同样用简并，但它是第二深度的回落**。表外余部（如立）首选初码 l（余音思路）；只有当 l 被更高频字占据时，次常用字才递归拆分、走简并 立→亠→d。

- 瞳(ts2m组)、僮(ts2r组)：各自组内 l 空闲 → 取初码 l
- 曈(ts2r组)：组内 l 已被更常用的僮(二级字)占用 → 曈(三级字)递归拆立 → 余部首传递 立→亠 → d 行 → ts2rd 空闲 → 取 d

**核心洞见**：简并不是主码专属——它是副码优先级链上"初码被占后"的递归回落手段，常用度决定谁拿初码 l、谁下沉到简并 d。与「晰」案例的余部首传递递归回落是同一机制在不同部件上的表现。设计动因：主码面对封闭部首集合，表外须映射回表内以维持部首表稳定；副码面对强声旁、开放集合的余字，表外部件直接取初码即可。

**理据**：瞳=目立(四码→桐)，僮(暂无)，曈=日亠(四码→佟，副码l→僮)。注：曈的四码冲突对象是 ts2r 组的佟，不是 ts2m 组的桐（初稿误写桐，已由 Amatiri 更正）。
