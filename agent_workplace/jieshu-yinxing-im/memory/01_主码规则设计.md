## 一、主码规则设计

### 重要概念区分:部首码、主码、副码

- **部首码**:查 `rules.md` 的部首表得到
- **主码**:编码的第4位(合体字取自部首码,独体字为数字)
- 二者路径完全不同,不可混淆。合体字主码取自部首码,但若该字自身在部首表中,部首码与主码可能不同(如「音」部首码 y,主码 r)。
- 独体字主码是数字,与部首码无关。
- **术语辨析补充**:
  - 见「部首」先看中心词--「部首码」中心词是"码"(查表,不拆),「部首传递」中心词是"部首"(拆字找部件)
  - 主码 = 整字部首(在表内)的部首码,三者形成严格传递链
  - 注意区分:部首别码 ≠ 余部首传递。别码是余字整体的部首码(不拆),传递要拆开余字找内部部首(拆)
- **部首码的正确理解**:
  - 部首码是**部首表的概念**,不是主码的概念
  - 任何部件只要在部首表中,就有部首码
  - 主码和副码都会参照部首码--主码取整字部首的部首码,副码在部首别码、余部分析等环节也会用到部首码
  - 副码分析中:部首别码就是余集合作为部首的部首码;音异取余音时,若余字是部首,其部首码等于初码(音托)

### 粗拆分与字义关联：辅助不显眼形旁判断

**来源**：用户提问「现代字形和形旁分离的字，根据规则优先取形旁（可能不在左上角）」。此节把 AI 早期回答中"大块拆分"这一**误称**纠正为**粗拆分**，并固化方法论。

#### 1. 粗拆分的精确定义

**粗拆分不是"找最大那块"，而是"把整字拆成几个大块"。**

两种思路的根本差异：

| 思路     | 核心动作  | 隐含假设                 | 错误后果                                  |
| ------ | ----- | -------------------- | ------------------------------------- |
| ❌ 找最大块 | 在部件里挑 | 部首 = 视觉上最大的部件        | 式归弋、萤归艹、舌归舌——全是错                      |
| ✅ 拆成大块 | 切整字   | 部首 = 切完后**余字成字**的那一刀 | 疆 = 土 + 彊（余字彊成字）✅；弓 + 三横 + 两田（余字不成字）❌ |

**"粗"的语义对照**：粗拆分 vs 细拆分——前者是 2-3 块的整体切割，后者是切到不可再分。粗拆分优先于细拆分。

#### 2. 粗拆分的核心约束

**约束 1：余字成字**

切完后剩下的部件**应尽量成字**，避免拆分出无意义的部件。这条直接对应 `rules.md` 3.1 的明确要求。

- 疆 = 土 + 彊 ✅（彊成字）
- 疆 = 弓 + 三横 + 两田 ❌（余字不成字）
- 萤 = 𫇦(艹+冖) + 虫 ✅（虫成字）
- 舌 = 千 + 口 ✅（口成字，且部首不自指）

**约束 2：独立明显，不交错、不穿插、不粘连**

切口的"干净度"决定粗拆分是否成立。这条对应 `rules.md` 3.1「"拆"要求独立明显，不交错、不穿插、不粘连」。

**约束 3：切口尽量少**

粗拆分的产物是 **2-3 块**，不是 5-6 块。这一条不是死规定，但体现了"先把字形分成几个语义整体"的方法论——粗拆分的目的就是**让语义中心暴露出来**，切得太细反而让"哪个部件是形旁"看不清。

#### 3. 字义关联——粗拆分之后的筛选器

粗拆分只决定**有几个候选部件**，字义关联才决定**哪一个是部首**。

**筛选规则**：

1. **形旁 > 声旁**：候选部件里，谁与字义核心直接相关，谁就是部首候选。声旁即使位置显眼、面积大，也不取。
2. **穿透外框取内**：包围/半包围结构里，外框可能是声旁或装饰，内里才是形旁。
3. **同族字一致性**：候选不唯一时，看同族字（同一声旁系列）的取部模式。
4. **现代字形兜底**：康熙部首/字源实在分不清时，现代字形提供最终答案（取左/上/外）。

> **横跨关系**：「粗拆分 + 字义关联」默认走康熙部首（因为康熙以形旁为主）。但康熙部首也会出现取声旁的现象——此时需要走**优化分配**纠正（`rules.md` 3.3）。这就是为什么「粗拆分 + 字义关联」**横跨康熙部首与优化分配**。

#### 4. 「粗拆分 + 字义关联」的典型应用

下表汇集**现代字形与形旁分离**的字，展示粗拆分如何穿透视觉干扰：

| 字   | 粗拆分结果（用解书拆分辅助） | 易混淆误取的其他部件 | 字义关联判断                             | 最终部首 |
| --- | -------------- | ---------- | ---------------------------------- | ---- |
| 粥   | rr. 弓 米 弓      | 弓          | 粥 = 米做的食物，米是形旁                     | 米    |
| 疆   | l. 彊 土         | 弓          | 疆 = 土的边界，土是形旁                      | 土    |
| 鹰   | l. 䧹 鸟         | 广          | 鹰 = 鸟类，鸟是形旁；广字头罩在外面是声旁             | 鸟    |
| 萤   | i. 𫇦 虫        | 艹          | 萤 = 萤火虫，虫是形旁                       | 虫    |
| 腾   | l. 朕(变体) 马     | 月          | 腾 = 马奔腾、上升，马是形旁；月旁是讹变构件            | 马    |
| 麾   | l. 麻 毛         | 麻          | 麾 = 旌旗之属（旄尾），毛是形旁；麻是声旁             | 毛    |
| 颖   | l. 顷 禾         | 页          | 颖 = 禾穗（颖本义），禾是形旁                   | 禾    |

**三种典型场景**：

| 场景         | 代表字     | 关键判断依据                   |
| ---------- | ------- | ------------------------ |
| 形旁被声旁覆盖    | 粥、疆、颖、式 | 形旁在视觉上"不大块"或被边缘化，但语义上是核心 |
| 形旁被外框/字头遮蔽 | 鹰、萤、腾、麾 | 形旁在内部，外面套着声旁或装饰性部件       |
| 现代字形模糊化    | 舌       | 字源上是合体，但康熙部首取自己，容易误判     |

#### 5. 粗拆分 ⊂ 解书拆分：层级关系定位

**粗拆分是解书拆分的第一步**——这是两个概念最关键的层级关系。

**解书拆分的拆分原则**（见 `rules.md` 五）原文：

> 「优先按明显结构拆分（左右→上下→包围）」

这正是**粗拆分的核心**。`rules.md` 五还给出了解书拆分的 6 种结构码（r. rr. i. ii. l. x.）和部件表示法，这套符号在表中用于辅助标注粗拆分结果（见第 4 节表格）。

**两者的区别**：

| 维度   | 粗拆分                       | 解书拆分                     |
| ---- | ------------------------- | ------------------------ |
| 拆分粒度 | 到「 2-3 个语义整体」为止（以余字成字为标志） | 递归拆到基础部件（部首双码、独体字码、扩展字根） |
| 目的   | 为部首选取提供候选部件               | 为主码和副码选取提供理论依据           |
| 终点   | 形旁识别出来即可                  | 拆到不可再分 / 可用代码表示          |

**典型示例：「颖」的拆分对比**：

- **粗拆分**：颖 = l. 顷 禾（一刀包围，切到「顷 + 禾」为止，余字「顷」成字，可以走字义关联）
- **解书拆分**：颖 = l. r. 匕 页 禾（继续拆「顷」为「r. 匕 页」），然后「匕、页、禾」分别转换为部首双码「bi ie he」，最后彻底字母化为「l. r. bi ie he」

可以看到：**`l.`（包围结构）是一脉相承的**——粗拆分用的结构码在解书拆分里被保留下来继续递归。粗拆分不是另起一套符号，而是**借用解书拆分的符号但停在第一步**。

**实操意义**：

- 遇到不显眼形旁时，**只需做粗拆分就足以判断部首**——不用把整字拆到底。
- 副码分析时才需要完整的解书拆分——因为副码要处理「余集合进一步拆分」的部件传递问题（见 `rules.md` 四）。

#### 6. 共性逻辑总结

四步走：

1. **粗拆分打底**——判断"是不是真的合体"、"哪几个块是稳定的"。
2. **字义关联筛选**——几个候选部件里，谁和字义核心相关，谁就是部首候选。
3. **形旁优先于声旁**——声旁即使占面积大、位置显眼，也不取。
4. **现代字形兜底**——康熙部首/字源实在分不清时，现代字形提供最终答案（取左/上/外）。

注：默认走康熙部首；康熙取了声旁时走优化分配纠正。

#### 7. 边界观察：视觉显眼度 ≠ 语义核心度

两个反直觉案例：

- **式**：弋在视觉上是"主体"（三笔横斜），工只是底下的小块，但解书取工不取弋。
- **萤**：艹是字头、最显眼，但解书穿透艹取虫。

**结论**：**粗拆分是基础，但"大块"不等于"对"。** 视觉上的显眼度和字义上的核心地位，在解书里是**两套独立的评分系统**——前者服务于"识别快不快"，后者服务于"归类准不准"。部首选的是后者，所以哪怕它小、哪怕它藏在里头，只要字义关联够强，就选它。

#### 8. 易犯错误（AI 历史教训）

早期 AI 回答中曾把"大块拆分"误用为"找最大那块"，导致错误地把部首与"视觉上最大的部件"绑定。这一错误已被纠正。**今后推导时遇到"哪个是部首"的疑问，第一动作应该是"粗拆分"，不是"找最大"。**

### 康熙部首中月部与肉部的区分

**月（yuè）和肉（ròu）在现代字形中写法相同（⺼），但在康熙部首体系中是两个独立的部，部首码不同。**

- **月部** → 部首码 **y**：表示月亮、时间等（如朗、朔、朝、期）
- **肉部** → 部首码 **r**：表示身体部位、器官（如肌、肝、胸、背、膺）

**编码一致性验证**：

| 肉部字 | 编码    | 主码  | 释义      |
| --- | ----- | --- | ------- |
| 肌   | ji1r  | r   | 肌肉      |
| 肝   | gj1r  | r   | 肝脏      |
| 胸   | xs1r  | r   | 胸部      |
| 背   | bz4r  | r   | 背部      |
| 胃   | wz4rt | r   | 胃部（带副码） |

膺 yīng（义愤填膺、荣膺）从肉部，主码 r → **y;1r**，非 y;1y。

**学习提示**：见到左侧 ⺼ 部件的字，先判断是身体部位（肉→r）还是时间/光亮（月→y）。康熙部首的区分在现代字形中已消失，但编码体系保留了这道分野——这对于理解汉字字源反而是帮助。

### 「服」字归月部的字源学背景

**关键细节**：「服 fú」编码 `fu2y`（主码 y，月部）——但「服」字源上不是月部、也不是肉部，而是「舟」部。

- 《说文解字》：「**服，从舟，𠬝聲**」——明确归**舟部**
- 本义：舟两旁的夹木（船舷板）
- 甲骨文/金文：左边是「舟」+右边「𠬝」（一只手按住一个人，会意"使服从"）
- 隶变/楷化过程：**舟旁讹变为月旁**（汉字讹变典型案例）
- 康熙字典：**遵从说文**，仍标"月"部（但本质上承认字源是舟）
- 解书音形：**遵从康熙部首** → `服 fu2y` 主码 y

**为什么解书不改正？**

1. **康熙部首是基础**——解书的现代字形优先不等于"纠正康熙"，而是在康熙体系上的优化分配
2. **重码考虑**——如果把"服"改归舟部（v），会和"舟"系列其他字大量重码
3. **历史传承**——大量字源"讹变"的字（其他如"脈"从"月"讹变、"脊"从"月"讹变等）都沿用康熙部首

**判断口诀**：见到含"⺼/月"偏旁的字，**先按"月 vs 肉"判别**（光亮/时间→y，身体/器官→r），**不要被字源"舟"等原始字形干扰**——解书遵从康熙，月/肉的二级区分是规则主线。

> 💡 **字源学上的意外惊喜**：解书对"服"归月部的处理，反而揭示了汉字**"舟→月"讹变**这一字源现象——这正是解书"严谨遵从康熙"带来的字源学价值。

### 优化分配补充：「倝」类部件可取「十」（S 行））

**规则**：重新根据现代字形认定「倝」的部首为「十」。康熙部首是人，但现代字形中次于“十”。对于以「倝」为声旁的字，若该字另有形旁在部首表中（非单笔画），则取形旁为部首；若形旁不在部首表中，则取「十」为部首。此规则在余部首传递中同样有效：余字「幹」的部首是「十」，因此「擀」的副码取余部首传递「幹→十」→ s。

**验证**：

- 乾 qm2s：形旁「乙」为单笔画不在表→取「十」s
- 擀 gj3us 副码 s：余字「幹」（形旁「干」不在表）部首十→s（余部首传递）
- 翰 hj4y：形旁「羽」在部首表→取 y
- 韩 hj2w：形旁「韦」在部首表→取 w
- 朝 ik2y/vk1y：形旁「月」在部首表→取 y

**来源**：编码实践沉淀的优化分配约定。康熙部首（人）在现代字形中地位较次，按左上原则取十。可视作一种不完全的部首简并。 

### 优化分配与表外部首处理的根本区分

**核心洞见**:这是部首编码流程中**先后衔接、功能互斥、地位悬殊**的两个独立阶段,绝不可混淆。

#### 逻辑前提的根本对立

| 维度       | 优化分配         | 表外部首处理       |
| -------- | ------------ | ------------ |
| **前提**   | 部首**未定**     | 部首**已定**     |
| **功能目标** | **决策**--选择部首 | **映射**--获取编码 |
| **输入**   | 存在歧义的汉字结构    | 已确定的部首部件     |
| **输出**   | 一个确定的部件      | 一个字母/数字(主码)  |
| **系统地位** | 锦上添花的**优化层** | 雪中送炭的**生存层** |
| **删除后果** | 性能退化,编码变难记   | 系统崩溃,无法编码    |

**关键区分**:

- "未定"与"已定"是二者最根本的分界线
- 优化分配管"选哪个",表外部首处理管"怎么编"
- 两者工作时序**绝对不可颠倒**:优化分配在前,表外部首处理在后

#### "跳过"的本质差异

- **优化分配中的跳过**:放弃A部件,改选B部件 → 输出新的部首选择
- **表外部首处理中的跳过**:放弃直接编码,改用整字替代 → 输出编码值

**逻辑灾难示例(部首"立")**:

如果将优化分配中的"跳过"延迟到表外部首处理阶段,会引发不可调和的矛盾:

1. 优化分配阶段已取"立"为部首(无法退回重选)
2. 表外部首处理阶段同时收到两条指令:
   - 指令A(部首简并):"立"简并为"亠",取码d
   - 指令B(跳过):"立"应跳过,改取其他部件
3. 结果:既要用这个部件编码,又要放弃这个部件 → **逻辑崩塌**

**结论**:优化分配中的跳过是**部首选择策略**,必须在选择阶段执行。

#### "罕部跳过"的正确归属

"罕部跳过"**是且仅是表外部首处理的一个特殊映射规则**。

它与以下规则并列,共同构成表外部首处理的完整工具集:

- 变体统一:给定变体部首 → 映射到正体部首的码
- 非部首字代替:给定非部首成字 → 映射到形似部首的码
- 部首简并:给定合体部首 → 映射到其组成部首的码
- **罕部跳过:给定罕用成字部首 → 以整字为单位映射到另一个部首的部首码**

其特殊性仅在于:它是唯一一个以整字为视角而非以部件为视角的映射规则。但无论视角如何,其操作对象始终是**已确定的部首**,操作目的始终是**获得编码**。由于类似"耐"的字无需优化分配,所以罕部跳过一定要在表外部首处理中,否则系统直接崩溃。

#### 系统重要性验证

- 删除优化分配中的跳过规则 → 系统仍可运行,零重码体系完整,只是编码不符合直觉
- 删除表外部首处理 → 所有不在《部首表》中的部首无法获得编码,零重码体系**立即崩溃**

**一个删除后系统变难用,一个删除后系统直接崩溃**--两者地位判若云泥。

### 码表中主码数据分析

本节统计了当前码表(约 7900 字)中主码分布的特征数据,以及设计含义。

#### 1. 独体字与合体字填充密度:3.11 倍的相对差异

按音区分组统计,每个音区独立计算填充率:

| 维度  | 平均每音区字数 | 理论容量 | 填充率       |
| --- | ------- | ---- | --------- |
| 独体字 | 0.279   | 10   | **2.79%** |
| 合体字 | 5.82    | 648  | **0.90%** |

**独体字填充密度是合体字的 3.11 倍**——但绝对填充率都很低,主码空间都没有被严重透支。这个 3.11× 的倍数是相对意义的,不能误读为「独体字严重透支而合体字宽松」。

**修正前的不当表述**：「独体字严重透支,合体字充裕」——这个二分法在绝对填充率层面都不成立。两者都远未填满。

#### 2. 独体字没有副码:「副码率」指标对独体字不适用

独体字(主码为数字)编码长度超 4 的 33 个字中:

- **15 个第一繁体**(以纯 `.` 结尾,如仟/隻/捌/贰/叁/習/鬥/東/柒/義/豐/乾/幹/夕/馬/氣)
- **17 个补码**(`.+字母`,如亖/宀/亠/廾/仂/榦/屮/卄/疒/𠂆/𥩖/気)
- **0 个「为消重而设的副码」**——独体字没有消重压力,超长都是补码驱动

**结论**:统计主码的「需副码率」时,应排除独体字(主码为数字者),或单独标注「需补码率」。「主码 4 需副码率 7.89%」这种说法不严谨,实际是需补码率。

#### 3. 独体字优先级倒挂:按辨认难度而非涵盖范围确定

| 优先级   | 主码    | 类别     | 字数     | 占比         |
| ----- | ----- | ------ | ------ | ---------- |
| 1     | 3     | 开形     | 21     | 5.80%      |
| 2     | 6     | 大形     | 37     | 10.22%     |
| 3     | 0     | 闭形     | 18     | 4.97%      |
| 4     | 5     | 称形     | 58     | 16.02%     |
| **5** | **4** | **错形** | **76** | **20.99%** |
| 6     | 7     | 偏形     | 44     | 12.15%     |
| 7     | 1     | 竖形     | 37     | 10.22%     |
| 8     | 2     | 横形     | 28     | 7.73%      |
| 9     | 9     | 复形     | 40     | 11.05%     |
| 10    | 8     | 奇形     | 3      | 0.83%      |

**核心洞见**:优先级前 3 名(开/大/闭)合计仅 76 字(21%),而优先级中段(4-6)合计 178 字(49%)。优先级与字数反相关。

**原因**:优先级按「视觉辨认难度」而非「涵盖范围」确定:

- **3 开形**排第一——「笔画分开」是最容易识别的特征,看一眼就归类。涵盖范围小,但判别成本最低。
- **4 错形**虽然判别难度不低,却是「排他性兜底」:笔画不分开?不大?不闭?不称?→ 默认落进错形。汉字多数是横竖撇捺交错的普通结构,所以错形吃最多字。
- **8 奇形**排最后——丩/乙/乂 这类字不属于任何常规类别,必须留一个主码位容纳。

**设计逻辑**:「先排除简单类别,再考虑复杂类别,最后兜底」。常用字优先落到易识别类别(开/大/闭/断),难归类的字进错形,真正无类可归的进奇形。「好打的字好归类,难打的字难归类」。

#### 4. u 占比高的真正原因:部首重磅而非数量

u 主码字数 996(12.61%)是部首表本身的设计结果,和「优化分配规则」**完全无关**。

- u 部首表收纳 9 个部首(攵/水/矢/手/食/山/士/豕/身),在 25 个字母中只排第 6——数量上不算最多
- **真正原因是部首高产**:u、r、k 是三个「高产部首」,每部首平均承载 100+ 字
- 对比 m(部首数 11)和 g(部首数 11),部首多不等于字多

**u 部首的语义分布**:

- **别码部首**:u 行中只有「攵」是别码部首(初码 p ≠ 部首码 u),且比较高频
- **音托部首**:水(u=初码 u)、手(u=初码 u)、食(u=初码 u)、山(u=初码 u)等都是音托部首,且**本身就是汉字最常用的基础语义部首**——水/手/食/山/身涵盖日常最高频语义

**u 的部首表设计**:把「日常高频语义部首」集中放在 u 行(以及 r、k),这些部首造字能力本身强,u 主码下自然积累大量字。**不靠数量取胜,靠每个部首都重磅**。

#### 5. u 不是「重灾区」:73% 编码无需消重

u 主码总字数 999,涉及 597 个音区(共 1296),需副码率 40.24%。**但需副码率 40.24% 是字数占比,不是码位利用率**:

- **(音区+主码)位置总数(只看合体字)**:5499 个
- **单字位置(77.01%)**:4235 个——这些位置**永远不需要副码**
- **多字位置(22.99%)**:1264 个——平均 2.62 字/位置,绝大部分只占 1-2 个副码位
- **极端位置**:yi4+u 是 34 字/位置(最高),是真正的「重灾区」,但只占 1 个位置

**整体看,合体字 73.59% 是空副码字(4 码),需副码字仅 26.41%**。这一统计印证了:

- 码表「常用字优先落到空副码」的设计意图
- 副码/补码是**局部补丁**而非**全局基础设施**——只为应对少数热区

u 不算「重灾区」的特征:

| 指标              | u 数值   | 长尾主码(f/v/l/o/p)数值 |
| --------------- | ------ | ----------------- |
| 字数              | 999    | 41-66             |
| 需副码率            | 40.24% | 2-13%             |
| 单字音区率           | 61.14% | 91-97%            |
| 多字位置数           | 1264   | 极少                |
| 极端音区(yi4+u=34字) | 有      | 无                 |

**u 确实是消重压力最明显的主码,但全局看「73% 编码无需消重」才是普遍特征**。长尾主码几乎不需消重,只有 u/m/c/r/b 等高产主码承担主要消重压力。

#### 6. 「分析音区」优于「分析主码」:管理功能 4 的设计依据

**主码视角的问题**:

- u 虽然占比 12.61% 最大,但分布极端(597 音区中有 365 个单字音区,61.14%)
- 从主码角度看 u,看不出普遍特征——单看「u 需副码率 40.24%」,会误判为「u 是重灾区」,但实际是「yi4+u 等少数位置局部拥挤」
- 主码维度的统计掩盖了「热区 vs 长尾」的差异,利用价值低

**音区视角的优势**:

- 直接锁定极端音区:yi4+u(34字)、yi8+u(12字)、vi4+u(7字)等
- 这些位置是真正的消重压力源,优化副码/补码规则时应聚焦这些位置
- 「音区+主码」是编码空间的最小单元,统计上每个位置的字数直接决定副码/补码压力

**结论**:管理功能 4 「分析音区」的设计正确——主码维度的全局统计会掩盖局部热区,音区维度的精确分析才能指导实际调控。

#### 7. 综合统计

| 维度                       | 数量       | 占比     | 设计含义            |
| ------------------------ | -------- | ------ | --------------- |
| 独体字总数                    | 362      | 4.58%  | 远低于合体字          |
| 合体字总数                    | 7538     | 95.42% | 主力              |
| 需副码字(≥5码)                | 2087     | 26.41% | 局部消重,非全局        |
| 空副码字(4码)                 | 5816     | 73.59% | 常用字直接命中         |
| 独体字超长                    | 33       | 9.11%  | 全为补码驱动          |
| 8 大主码(u/m/r/k/c/b/y/s)合计 | 4465     | 56.52% | 部首高产集中的体现       |
| 涉及音区数(u)                 | 597/1296 | 46.07% | 不均匀分布           |
| 单字音区数(u)                 | 365/597  | 61.14% | 大部分 u 字所在音区无需消重 |
| yi4+u 极端位置               | 34 字     | 1 个位置  | 真正的消重重灾区        |

**核心洞见汇总**:

1. **绝对填充率都低**——独体 2.79%、合体 0.90%,均无「严重透支」
2. **u 不是优化分配产物**——是部首表本身把高频语义部首集中
3. **73% 编码无需消重**——副码/补码是局部补丁
4. **独体字优先级按判别难度**——错形最多字是「排他性兜底」
5. **分析音区优于分析主码**——主码维度掩盖局部热区
